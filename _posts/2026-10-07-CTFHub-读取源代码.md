# CTFHub Writeup - 读取源代码

## 题目类型

WEB

## 题目描述

打开题目，点开链接后，题目显示一段代码：

<?php
error_reporting(E_ALL);
if (isset($_GET['file'])) {
    if ( substr($_GET["file"], 0, 6) === "php://" ) {
        include($_GET["file"]);
    } else {
        echo "Hacker!!!";
    }
} else {
    highlight_file(__FILE__);
}
?>
<hr>
i don't have shell, how to get flag? <br>
flag in <code>/flag</code>

下面有一行英文：

i don't have shell, how to get flag?
flag in /flag

# 解题过程

## 踩坑过程

分享题目发现截图里的源码：

if ( substr($_GET["file"], 0, 6) === "php://" ) {
    include($_GET["file"]);
}

明确规定了 file 参数前6个字符必须、且只能以 php:// 开头

于是尝试在 ?file= 参数里直接拼接 flag.php 和 /flag

回车后发现页面弹窗 Hacker!!! 或一片空白。判断出靶场源码过滤了 flag 关键词，并且包含直接执行会导致 PHP 代码无法显示

选择进行尝试 data:// 伪协议

在浏览器输入 靶机地址?file=data://text/plain;base64,PD9waHAgc3lzdGVtKCdjYXQgL2ZsYWcnKTsgPz4=

依然弹窗 Hacker!!!，说明靶场对 data:// 协议或者后面的 Base64 特征也做了黑名单拦截

再次尝试 php://filter 读源码

输入靶场地址 ?file=php://filter/convert.base64-encode/resource=/flag

弹窗 Hacker!!!。因为 flag 关键词直接暴露在了 URL 里

于是利用 URL 编码绕过，输入靶场地址 ?file=php://filter/convert.base64-encode/resource=/fl%61g

页面刷出了一串 Base64 乱码 Y3RmaHViezM2NWFiNjJhODgxZmZkYTUzZjNjN2Y0N30K

复制去在线网站解码，拿到了 ctfhub{365ab62a881ffda53f3c7f4}

结果陷入“环境重置”的死循环

拿着刚刚解出来的 ctfhub{365ab62a...} 去 CTFHub 提交

右侧弹出了一长串 Flag错误 的红色提示

以为是浏览器缓存了旧网页，于是反复刷新浏览器，重新复制上面同一个 URL 的 Base64 乱码去解码，发现出来的依然是 365ab62a...，提交依然失败

因为 CTFHub 靶场的“自动重置”陷阱。你在旧环境里抓的 Flag 已经失效了，新环境的 Flag 变了，而浏览器缓存了旧页面的结果

于是我决定使用Burp Suite

试图用 php://input POST 打法。

Burp 抓包发送到 Repeater，第一行改成 POST /?file=php://input，请求头加 Content-Type，算好 Content-Length: 26，Body 写 <?php system('cat /flag'); ?>。

Burp 的 Response 依然只回显了 i don't have shell...，执行失败（大概率是 Content-Length 算错了，或者是环境已经彻底烂了）

我决定重新尝试利用URL编码绕过这一方法

## 新路径
重新开启新环境，拿到新地址 challenge-b570fed3c8d3788d，直接再次访问 ?file=php://filter/convert.base64-encode/resource=/fl%61g

成功拿到新 Base64 Y3RmaHViezFkYmVkMjk3MGVjZDI1MTc2MmE3ZTk5Y30K，解码得到 ctfhub{1dbed2970ecd251762a7e99c}

# 笔记

## 失败原因

1.前面链接全弹 Hacker!!!？的原因：
 

源码的强制校验 + 关键词黑名单双重拦截

• 源码的强制性规定：你看源码第一行写着：if ( substr($_GET["file"], 0, 6) === "php://" )。它强制要求你的 file 参数前 6 个字符必须是 php://。

你如果直接写 ?file=flag.php 或 ?file=data://...，前6个字符不对，直接进入 else 分支，无脑弹你 Hacker!!!。

• flag 关键词黑名单：当你用了 ?file=php://filter/resource=/flag 时，前缀对了，但是靶场源码里还偷偷藏了一个检测（比如检测字符串里是否含有 flag 或 data 等敏感词）。

只要你 URL 里含有 flag，它也会报警弹 Hacker!!!。

• %61 的魔法：这就是为什么昨天我把 flag 改成 fl%61g，它就不弹了。

因为服务器看到的是 %61，正则匹配不到 flag 这个词，成功躲过检测；而服务器在处理参数时，会自动把 %61 解码成字母 a，最终依然正确读取了 /flag 文件。 
 
2.抓包（php://input POST）抓不出来的原因：
 
细节失误（主要是 Content-Length 和空行）。

• Burp 发送 POST /?file=php://input HTTP/1.1，请求体里写 <?php system('cat /flag'); ?>。

• 因为 HTTP 协议极其死板。必须在请求头和请求体之间保留一个空行，且 Content-Length 必须精准等于请求体的字节数（一个字都不能差）。

多打了一个空格、少按了一个回车，或者 Content-Length 算错了（比如把 26 算成了 25 或 27），服务器就会“读不懂”你的请求，进而直接抛弃你的 Body 内容，回显原本的空页面。

• 结论：能用 GET 浏览器直接拼 URL 解决的，就千万别开 Burp 去折腾 Content-Length，那是给自己找罪受。 
 
3.正确方法昨天抓出来的 Flag，提交却提示“错误”的原因：
 
CTFHub 靶场的“动态 Flag 刷新机制”。

• 靶场里的 /flag 文件内容不是静态的，它会动态生成。

• 昨天你抓出 ctfhub{365ab62a881ffda53f3c7f4} 时，那确实是当时环境里真实的 Flag。

但你提交时，可能环境倒计时快到了，或者后台自动帮你重置了一次，或者你在反复刷新中触发了环境重启。

• 一旦环境重置，服务器里的 Flag 文件内容就会瞬间变成另一串字符串。你手里拿的是“旧环境的旧钥匙”，去开“新环境的新锁”，当然会一直提示 Flag错误。 

## 这道题主要学习了：

1、php://filter 伪协议读取源码的核心原理

这道题最大的技术考点就是 php://filter。

当直接包含 PHP 文件时，代码会被当作脚本执行（导致白屏）；而利用 read=convert.base64-encode 过滤器，可以让服务器在读取文件时先进行 Base64 编码输出。

这样一来，脚本引擎就不认识它了，源码就会被当作纯文本完整地回显在页面上。这是一个“将执行变为展示”的经典思路。
 
2、源码审计与强制前缀规则的识别

通过审计源码发现 substr($file, 0, 6) === 'php://' 这一限制，学会了不能盲猜路径，

而是要顺着代码的逻辑去选择正确的协议。

只要前六个字符不对，就会直接触发 Hacker!!! 阻断。
 
3、WAF/黑名单关键词的绕过思维

当 flag 关键词出现在 URL 中时，触发了服务器内置的黑名单拦截。

掌握了用 URL 编码（将 a 替换为 %61，即 fl%61g）来绕过简单的字符串正则匹配，同时也印证了“黑名单防御机制非常容易被绕过”的原理。
 
4、GET 请求与 POST 请求的实战权衡（踩坑总结）

在 CTF 中，能用浏览器直接拼接 URL 解决的，绝不优先用 Burp Suite 去发 POST 包。

因为 POST 包需要严格计算 Content-Length 和保留空行，在极度疲惫时极易算错导致请求被服务器丢弃（这也是你昨晚抓包失败的核心原因）。
 
5、CTFHub 靶场“动态 Flag”机制的深刻教训

CTFHub 的靶场是动态生成的，每次重启或环境过期，服务器里的 Flag 内容都会重新随机生成。

在旧环境抓到的 Flag 提交到新环境，必然会提示 Flag错误。

遇到这种情况，不要怀疑自己的 Payload，而应立刻销毁并重建环境，重新抓取源码，一气呵成地完成提取和解码，快速提交。
