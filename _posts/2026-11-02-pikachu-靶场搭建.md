# 从 Docker 超时到 phpStudy 跑通：Pikachu 靶场搭建踩坑实录
> 一次从零开始的 Web 安全靶场搭建记录：Docker 方案因校园网失败，转投 phpStudy 成功，附数据库排错过程、环境配置心得，以及两个入门关卡的实战。
## 一、环境与目标
| 项目 | 内容 |
| --- | --- |
| 操作系统 | Windows 10 / 11 |
| 网络环境 | 校园网（对境外镜像源不友好） |
| 方案一 | Docker Desktop + 国内镜像加速 |
| 方案二 | 小皮面板 phpStudy（最终采用） |
| 最终环境 | Apache 2.4.39 + MySQL 5.7.26 + PHP 7.3.4 NTS |
| 目标 | 本地跑通 Pikachu，开始按模块刷题 |
选择 Pikachu 的原因很简单：它把常见的 Web 漏洞按模块拆好，SQL 注入、XSS、CSRF、文件上传、RCE 都有独立页面，适合从「照着敲」过渡到「自己判断」。
真正花时间的不是刷题，而是把环境跑起来。下面把两条路线和踩过的坑完整记一遍。
## 二、方案一：Docker 搭建（失败）
### 2.1 安装 Docker Desktop
1. 到 Docker 官网下载 Windows AMD64 版本并安装；
2. 安装完成后启动 Docker Desktop，跳过账号登录；
3. 确认 `docker version` 能正常输出版本信息。
### 2.2 配置国内镜像加速
由于 Docker Hub 访问不稳定，在 `Settings -> Docker Engine` 里加了几个国内加速器：
```json
{
  "registry-mirrors": [
    "https://docker.1ms.run",
    "https://docker.xuanyuan.me"
  ]
}
```
保存后重启 Docker Engine，用 `docker info` 确认镜像源已经生效。
### 2.3 拉取 Pikachu 镜像
```bash
docker pull 8023/pikachu-expect:latest
```
### 2.4 失败现象与原因
镜像大约 197MB，下载过程中反复出现两类报错：
```text
TLS handshake timeout
unexpected EOF
```
尝试过换镜像源、重试、重启 Docker，结果都差不多。原因大致有三点：
- 校园网对大流量、长连接有限制，下载到一半容易断；
- 部分国内加速器只缓存热门镜像，Pikachu 这种冷门镜像还是要回源；
- Docker 的分层下载一旦某层失败，整体就要重来。
结论：**不是 Docker 不好，是当前网络不适合拉大镜像**。与其继续和网络较劲，不如换一条不依赖外网的路。
## 三、方案二：phpStudy 搭建（成功）
### 3.1 安装小皮面板
访问 [小皮面板官网](https://www.xp.cn/)，下载 Windows 64 位版本并安装。安装完成后启动面板，准备 Apache 和 MySQL。
### 3.2 部署源码
从 GitHub 下载源码：
```bash
https://github.com/zhuifengshaonianhanlu/pikachu
```
解压后放到 `D:\Pikachu`。这里有一个很容易踩的坑：
- 解压后往往多一层同名文件夹，比如 `D:\Pikachu\pikachu\index.php`；
- 网站根目录必须**直接包含** `index.php`，也就是 `D:\Pikachu\index.php`。
如果路径套了一层，访问首页就会 403 或目录列表，后面 `install.php` 也会 404。
### 3.3 创建网站
在面板左侧点击「网站」→「创建网站」，按下表填写：
| 配置项 | 值 |
| --- | --- |
| 域名 | `pikachu` |
| 根目录 | `D:/Pikachu` |
| PHP 版本 | `php7.3.4nts` |
| 同步 hosts | 勾选 |
然后在面板里启动 Apache 2.4.39 和 MySQL 5.7.26。
### 3.4 配置数据库
1. 在「数据库」里修改 root 密码。面板对密码长度有要求（至少 6 位），这里设为 `rootroot`；
2. 新建一个数据库，名字叫 `pikachu`；
3. 打开 `D:\Pikachu\inc\config.inc.php`，把连接参数改成自己的：
```php
define('DBHOST', '127.0.0.1');
define('DBUSER', 'root');
define('DBPW', 'rootroot'); // 改成你设置的密码
define('DBNAME', 'pikachu');
define('DBPORT', '3306');
```
这一步是整条链路的关键：PHP 靠这个文件找到 MySQL。密码、库名、端口任何一项不对，页面都会报 Database Error。
### 3.5 初始化安装
浏览器访问：
```text
http://pikachu/install.php
```
点击「进行初始化安装」，看到「安装成功」后进入靶场首页，环境就通了。
### 3.6 验证
- 首页能正常打开，左侧模块列表完整；
- 随便点开一个关卡，页面不报数据库错误；
- 在面板里能看到 Apache、MySQL 都处于运行状态。
## 四、踩坑记录
| 现象 | 可能原因 | 解决方式 |
| --- | --- | --- |
| 403 Forbidden | 根目录套了一层文件夹，或目录没有读权限 | 确保 `index.php` 直接在站点根目录 |
| 404 / install.php 打不开 | 站点根目录配错、域名没同步 hosts | 检查网站根目录和 hosts |
| Database Error | 数据库密码、库名、端口与 `config.inc.php` 不一致 | 逐项核对参数，先用命令行连一次 |
| 端口被占用 | 80 或 3306 被其他服务占用 | 停掉占用服务，或改端口 |
| Docker TLS timeout | 校园网限制、镜像源回源失败 | 换网络或改用集成环境 |
| 页面空白 | PHP 报错被关闭 | 打开 `display_errors` 看具体错误 |
## 五、我学到了什么
### 5.1 一个 Web 靶场的三层结构
以前觉得「网站」是一个整体，搭完才发现它是三层拼起来的：
- **Web 服务器（Apache）**：接收请求，决定把哪个文件交给 PHP；
- **PHP**：执行代码，需要数据库时发起连接；
- **MySQL**：存数据，返回查询结果。
一次请求的链路大致是：
```text
浏览器 -> Apache -> PHP -> MySQL -> PHP 拼 HTML -> 浏览器渲染
```
任何一层出问题，页面都会「打不开」，但原因完全不同。学会按层排查，比记住某个报错怎么修更重要。
### 5.2 路径、端口、权限：环境问题的三大来源
折腾一下午，绝大多数问题都能归到这三类：
- **路径**：文档根目录指向哪、`index.php` 在不在根、`config.inc.php` 路径对不对；
- **端口**：80 被谁占了、MySQL 是 3306 还是 3308、防火墙有没有放行；
- **权限**：目录能不能读、文件能不能写、PHP 有没有权限连数据库。
这三类问题的共同点是：**报错信息往往不直接告诉你原因**。比如 403 可能是路径，也可能是权限；Database Error 可能是密码，也可能是端口。所以要把「现象」和「原因」分开，一项一项排除。
### 5.3 Docker 与集成环境的取舍
两种方式没有绝对好坏，只有适不适合：
| 维度 | Docker | phpStudy |
| --- | --- | --- |
| 隔离性 | 好，环境不污染本机 | 一般，装在本机 |
| 可移植性 | 好，一条命令起环境 | 差，换机器要重装 |
| 依赖网络 | 强，拉镜像看网络脸色 | 弱，装完就能用 |
| 排错难度 | 高，要懂容器网络和挂载 | 低，面板可视化 |
这次选择 phpStudy，不是因为它更「专业」，而是因为它在当前网络下**能最快跑通**。学习阶段，先让环境可用，再谈工程化。
### 5.4 数据库连接排错方法论
遇到 Database Error，我后来固定按这个顺序查：
1. 用命令行连一次：`mysql -h127.0.0.1 -uroot -p`，确认账号密码没问题；
2. 确认库存在：`show databases;` 里有没有 `pikachu`；
3. 对照 `config.inc.php` 的五个参数，逐字核对；
4. 看 PHP 的真实报错，而不是只看「Database Error」这一句；
5. 确认 PHP 版本和 MySQL 版本兼容（比如旧版 `mysql_*` 函数在新 PHP 里不可用）。
这套顺序能避免「凭感觉改配置」，也能快速定位是账号问题还是代码问题。
### 5.5 漏洞的本质：数据和代码没有边界
刷前两个关卡时，最直接的感受是：**漏洞不是「功能坏了」，而是「数据被当成了代码」**。
- 反射型 XSS：用户输入被原样拼进 HTML，浏览器把数据当脚本执行；
- SQL 注入：用户输入被原样拼进 SQL，数据库把数据当语句执行。
两者的根因完全一样：**没有区分「数据」和「代码」**。所以防御思路也一致——在数据进入代码的地方做转义或参数化，而不是在入口处删几个关键词。
### 5.6 一套可复用的排错习惯
- **先跑最小闭环**：静态页 → PHP 页 → 连数据库，每加一层验证一次；
- **一次只改一处**：同时改密码、端口、路径，出问题就不知道是谁的锅；
- **保留原始报错**：截图或复制完整报错，搜索关键词比自己猜快得多；
- **记录环境版本**：Apache、PHP、MySQL 的版本会影响函数和语法；
- **写文档复盘**：把踩过的坑写下来，下次换环境能少走一半弯路。
## 六、两个入门关卡
### 6.1 反射型 XSS
原理：后端把用户输入直接回显到页面，没有做 HTML 编码。
Payload：
```html
<script>alert('hacked')</script>
```
为什么能成：浏览器拿到响应后，会把 `<script>` 当代码执行，而不是当文字显示。
防御：输出时做 HTML 实体编码，比如 PHP 的 `htmlspecialchars()`；再配合 CSP 和 HttpOnly 兜底。
### 6.2 SQL 注入
原理：用户输入被拼进 SQL 语句，改变了原本的语义。
Payload：
```sql
admin' or 1=1 #
```
为什么能成：`'` 提前闭合了字符串，`or 1=1` 让条件恒真，`#` 注释掉后面的内容，登录校验就被绕过了。
防御：使用预编译语句（PDO 或 PreparedStatement），把输入当参数绑定，而不是拼字符串。
