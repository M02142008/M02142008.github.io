# 宽字节注入 通关笔记
> 这一关最反直觉：**代码明明调用了转义函数，但注入照样成立。**
>
> 问题不在函数，在**字符集**。
---
## 一、环境与目标
| 项目 | 内容 |
| --- | --- |
| 靶场 | Pikachu |
| 关卡位置 | SQL-Inject → 宽字节注入 |
| 页面地址 | `http://pikachu/vul/sqli/sqli_widebyte.php` |
| 提交方式 | POST |
| 参数名 | `name` |
| 目标 | 绕过 `escape()` 的转义 |
页面提示：
> kobe/123456，先搜索下什么是宽字节注入搞懂了再来测试吧

## 二、我的解题步骤
### 步骤 1：先正常查
输入 `kobe`：
```
your uid:3
your email is: kobe@pikachu.com
```
### 步骤 2：试普通 payload，被转义
输入 `kobe' or 1=1#`：
**没有结果，也没有报错。**
因为源码里有这一行：
```php
$name = escape($link,$_POST['name']);
```
`escape()` 内部是 `mysqli_real_escape_string()`，它会把 `'` 转成 `\'`。
SQL 变成：
```sql
select id,email from member where username='kobe\' or 1=1#'
```
`\'` 被当成"转义后的单引号"，是**字符串内容**，闭合不了。
payload 失效。
### 步骤 3：注意到字符集是 GBK
源码里有一行很关键：
```php
//设置mysql客户端来源编码是gbk,这个设置导致出现宽字节注入问题
$set = "set character_set_client=gbk";
execute($link,$set);
```
**客户端字符集是 GBK。**
### 步骤 4：用宽字节"吃掉"反斜杠
payload 前面加一个 `%df`（0xDF）：
```
%df' or 1=1#
```
实际发送的字节：
```
DF 27 20 6F 72 20 31 3D 31 23
 ↑  ↑
df  '
```
`escape()` 把 `27`（`'`）转义成 `5C 27`（`\'`），所以实际变成：
```
DF 5C 27 20 6F 72 20 ...
```
**关键来了**：在 GBK 编码里，`DF 5C` 是一个合法的双字节汉字（"運"）。
所以 MySQL 解析时：
- `DF 5C` → 一个汉字
- `27` → **重新变回了一个独立的单引号**
SQL 变成：
```sql
select id,email from member where username='運' or 1=1#'
```
**闭合成功。**
### 步骤 5：结果
我实测：
| 输入 | 返回 |
| --- | --- |
| `kobe` | **1 条** |
| `%df' or 1=1#` | **7 条**（整张表） |

## 三、原理分析
### 3.1 源码
```php
if(isset($_POST['submit']) && $_POST['name']!=null){
    $name = escape($link,$_POST['name']);
    $query="select id,email from member where username='$name'";//这里的变量是字符型，需要考虑闭合
    //设置mysql客户端来源编码是gbk,这个设置导致出现宽字节注入问题
    $set = "set character_set_client=gbk";
    execute($link,$set);
    //mysqi_query不打印错误描述
    $result=mysqli_query($link, $query);
    ...
}
```
**转义有了，但字符集没配对——功亏一篑。**
### 3.2 逐字节看发生了什么
原始输入：
```
DF 27
```
`mysqli_real_escape_string` 在 `'`（27）前加 `\`（5C）：
```
DF 5C 27
```
MySQL 用 **GBK** 解析这个字节流：
| 字节 | GBK 解释 |
| --- | --- |
| `DF 5C` | 一个完整的汉字（"運"） |
| `27` | 独立的单引号 |
**所以反斜杠被"吃掉"了，单引号又活了过来。**
### 3.3 为什么换成 UTF-8 就没事
UTF-8 是**变长编码**，但有一个特性：
> **UTF-8 的每个字节都不会是另一个字符的"前半部分"被误读。**
具体来说：
- GBK 用 0x81~0xFE 作为双字节的首字节
- `0x5C`（反斜杠）在 GBK 里是合法的**第二字节**
- 所以 `DF 5C` 会被合并成一个字
而 UTF-8 要求每个多字节序列的后续字节都在 `0x80~0xBF` 之间，`0x5C` 不在这个范围——**不会被合并。**
**所以宽字节注入是 GBK / GB2312 / BIG5 这类编码专属的问题。**
### 3.4 常见的"吃掉反斜杠"的字节
| payload 前缀 | 说明 |
| --- | --- |
| `%df` | 最经典 |
| `%bf` | 也可用 |
| `%81`~`%fe` | 理论上很多都行，实际看编码表 |

## 四、知识点与笔记
### 4.1 宽字节注入成立的两个条件
| 条件 | 说明 |
| --- | --- |
| **数据库连接用了宽字符集** | `set character_set_client=gbk` |
| **转义函数不认识这个字符集** | `mysqli_real_escape_string` 按"当前字符集"转义，但转义只加反斜杠，不理解 GBK 的双字节 |
**两个条件缺一不可。**
### 4.2 为什么 `addslashes()` 更容易中招
```php
$name = addslashes($_POST['name']);
```
`addslashes()` **完全不考虑字符集**，只会在 `'` `"` `\` 前加 `\`。
**只要数据库是 GBK，一个 `%df` 就绕过了。**
### 4.3 复现的最小环境
```php
mysqli_query($link, "set character_set_client=gbk");
mysqli_query($link, "set character_set_results=gbk");
$name = mysqli_real_escape_string($link, $_POST['name']);
$sql = "select * from t where name='$name'";
```
payload：`%df' or 1=1#`
### 4.4 历史上著名的案例
宽字节注入在早期的中文 CMS（织梦、帝国、Discuz 等）里非常常见。
原因：
- 国内服务器常用 GBK
- 老代码用 `addslashes` 或 `mysql_escape_string`
- 连接字符集没显式设置
**这是"中文环境专属"的一类注入。**

## 五、和其他几关的区别
| 关卡 | 有没有转义 | 能不能注入 |
| --- | --- | --- |
| 字符型 | 没有 | 能（直接闭合） |
| **宽字节** | **有 `escape()`** | **能（吃掉反斜杠）** |
**这一关是"防御方式用错了"，不是"没有防御"。**

## 六、防御怎么写
### 6.1 根本：参数化
```php
$stmt = $link->prepare("select id,email from member where username=?");
$stmt->bind_param('s', $name);
$stmt->execute();
```
**参数化不涉及"转义"，所以没有字符集的问题。**
### 6.2 用 `mysqli_set_charset` 而不是 `SET NAMES`
```php
// 推荐：会同时设置 client/result/connection
mysqli_set_charset($link, 'utf8mb4');
// 不推荐：只设置了 character_set_client
// mysqli_query($link, "SET NAMES gbk");
```
`mysqli_set_charset()` 会**同时更新驱动层的字符集认知**，`mysqli_real_escape_string` 才知道该怎么转义。
### 6.3 统一用 utf8mb4
```sql
-- 建库
CREATE DATABASE app DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_unicode_ci;
-- 建表
CREATE TABLE t (...) DEFAULT CHARSET=utf8mb4;
```
**从库到连接，全部 utf8mb4，宽字节注入就无从下手。**
### 6.4 为什么不推荐"过滤 `%df`"
又是黑名单思路：
- `%df` 被拦 → 换 `%bf`、`%81`……
- 换个编码方式又绕过
**黑名单永远堵不完。**

## 七、总结
| 要点 | 内容 |
| --- | --- |
| 这关教什么 | 转义 + 错误字符集 = 白转义 |
| payload | `%df' or 1=1#` |
| 原理 | `DF 5C` 在 GBK 里是一个汉字，`27` 重新变成单引号 |
| 实测 | 1 条 → 7 条 |
| 修复 | 参数化 + `mysqli_set_charset('utf8mb4')` |
**一句话**：
> **转义函数是对的，字符集是错的——两个"对"凑在一起，反而成了漏洞。**
