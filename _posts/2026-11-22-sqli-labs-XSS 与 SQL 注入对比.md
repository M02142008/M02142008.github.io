# XSS 与 SQL 注入 对比笔记

> 学完 Pikachu 的 XSS 和 SQL 注入模块后，最想问的一个问题：
>
> **这两个东西看起来完全不一样，为什么老师说它们是"一类"？**
>
> 这篇笔记就是把它们放在一起对照。

---

## 一、一句话结论

> **XSS 和 SQL 注入是同一个病根，长在两个不同的地方。**
>
> **病根：程序把"用户输入"和"代码"拼在了一起，导致输入越界成了代码。**
>
> **区别：XSS 的代码在浏览器里跑，SQL 注入的代码在数据库里跑。**

---

## 二、共性：病因完全一样

### 2.1 同一张图

```
【正常情况】数据和代码是分开的

  程序固定部分：  SELECT * FROM users WHERE id = ?
  用户填的内容：  1

  两者互不影响


【出事情况】数据和代码被拼成了一条字符串

  程序：  "SELECT * FROM users WHERE id='" + 用户输入 + "'"

  用户输入：  1' union select 1,2,3 --+

  拼出来：
  SELECT * FROM users WHERE id='1' union select 1,2,3 --+ '

  ★ 用户输入越界，变成了命令 ★
```

**XSS 是同一件事，只是换了语言：**

```javascript
// 程序
element.innerHTML = "<div>" + 用户输入 + "</div>"

// 用户输入
<img src=x onerror=alert(1)>

// 拼出来
<div><img src=x onerror=alert(1)></div>
```

### 2.2 四条共性

| # | 共性 | 具体表现 |
| --- | --- | --- |
| 1 | **都是“注入”** | 用户输入被当成代码执行 |
| 2 | **病根都是“字符串拼接”** | 数据和代码没有边界 |
| 3 | **都依赖“上下文”** | XSS 看 HTML/JS 上下文；SQLi 看 SQL 上下文 |
| 4 | **防御思路同源** | 不拼接、按上下文转义、白名单 |

### 2.3 第 4 条最关键

真正有效的修复，本质是同一件事：

| | XSS | SQL 注入 |
| --- | --- | --- |
| 核心做法 | **输出时按上下文编码** | **预编译（参数化查询）** |
| 效果 | 用户的输入永远是“文本” | 用户的输入永远是“数据” |
| 共同点 | **把用户输入锁在“值区”里，永远出不来** |

**（“值区”的概念见 Less-1 那篇笔记 3.1 节。）**

### 2.4 同一个家族

| 漏洞 | 数据 | 代码 | 越界方式 |
| --- | --- | --- | --- |
| SQL 注入 | `1` | `SELECT ...` | 数据被当 SQL 解析 |
| XSS | `hello` | `<div>...</div>` | 数据被当 HTML 解析 |
| 命令注入 | `127.0.0.1` | `ping ...` | 数据被当 shell 命令解析 |
| 模板注入 | `{{7*7}}` | 模板语法 | 数据被当模板表达式解析 |

**Pikachu 里这几关，其实是同一个病根的四种长相。**

---

## 三、区别：注入点和执行者不同

### 3.1 一张图看清

```
XSS：

  攻击者输入
      ↓
  存进网页（HTML 里）
      ↓
  ★ 受害者的浏览器 ★ 解析执行
      ↓
  偷 cookie / 钓鱼 / 蠕虫传播


SQL 注入：

  攻击者输入
      ↓
  拼进 SQL 语句
      ↓
  ★ 数据库服务器 ★ 解析执行
      ↓
  脱库 / 改数据 / 删表
```

### 3.2 完整对比表

| 维度 | XSS | SQL 注入 |
| --- | --- | --- |
| 注入到哪 | 网页（HTML/JS） | SQL 语句 |
| 谁来执行 | **受害者的浏览器** | **数据库引擎** |
| 被害者是谁 | **访问网站的用户** | **网站/公司** |
| 攻击语言 | HTML、JavaScript | SQL |
| 门槛 | 低（`alert(1)` 就能验证） | 中（要判断闭合、列数、回显位） |
| 典型危害 | 盗 cookie、钓鱼、蠕虫 | 脱库、改数据、删库 |
| 是否需要回显 | 不需要（盲打也能打） | 不一定（盲注也能打） |
| 怎么发现 | 看输入有没有原样输出 | 看报错、看回显、看响应时间 |
| 最有效防御 | 输出时按上下文编码 | **预编译（参数化查询）** |
| 辅助防御 | CSP、HttpOnly Cookie | 最小权限、关闭报错 |

### 3.3 三个最本质的差异

#### 差异一：受害对象不同

| | XSS | SQL 注入 |
| --- | --- | --- |
| 丢的是什么 | **用户的 cookie / 登录态** | **网站的数据库** |
| 谁承担损失 | 用户 | 公司 |

**SQL 注入像“把仓库搬空”，XSS 像“冒充店员骗顾客”。**

#### 差异二：代码在哪运行

| | XSS | SQL 注入 |
| --- | --- | --- |
| 执行环境 | 浏览器（客户端） | 数据库（服务端） |
| 攻击者实际控制的是 | 别人的浏览器 | 数据库的语句 |

**这也决定了“修复位置”不同：**

- XSS 修复在**输出时**（`htmlspecialchars`）
- SQL 注入修复在**查询构造时**（`prepare`）

#### 差异三：门槛和收益不同

| | XSS | SQL 注入 |
| --- | --- | --- |
| 入门 | 一学就会（弹个窗） | 要先懂 SQL 语法 |
| 危害上限 | 控制管理员账号、蠕虫式传播 | **拖走整个数据库** |
| 现在的防护 | CSP 让利用变难 | 预编译让注入变难 |

## 四、传递方式的对照

两种漏洞都有“不同送达方式”，这是做题时最容易混淆的地方。

### 4.1 XSS 的分类

| 类型 | 数据怎么到浏览器 |
| --- | --- |
| 反射型 | 服务器把 URL 参数原样写进 HTML |
| 存储型 | 存进数据库，别人访问页面时读出来 |
| DOM 型 | 服务器不参与，前端 JS 自己拼进页面 |
| 盲打 | 数据存在"后台"，管理员查看时才触发 |

### 4.2 SQL 注入的分类

| 类型 | 数据怎么反映到页面 |
| --- | --- |
| 联合注入 | 直接把结果 `union` 到回显位 |
| 报错注入 | 借报错信息把数据带出来 |
| 布尔盲注 | 只能看出"对/错" |
| 时间盲注 | 只能靠响应快慢判断 |

### 4.3 对照着看

| 共同思路 | XSS | SQL 注入 |
| --- | --- | --- |
| **有回显** | 反射型 / 存储型 | 联合注入 |
| **没回显** | 盲打 | 盲注 |
| **完全不经过服务器** | DOM 型 | （无对应） |

**这个对照很有用：遇到"有回显"就用直接方法，遇到"没回显"就用间接方法。**

## 五、攻防对照

### 5.1 防御手段一一对应

| 要防的问题 | XSS 的做法 | SQL 注入的做法 |
| --- | --- | --- |
| **根本解：数据和代码分离** | 输出编码 | 预编译 |
| **减少影响面** | HttpOnly Cookie、CSP | 最小权限、独立账号 |
| **不泄露信息** | 统一错误页 | 关闭 `display_errors` |
| **输入层兜底** | 白名单、长度限制 | 类型转换（`intval`） |

### 5.2 代码层面

**XSS 的正确写法：**

```php
// 错误
echo "<div>" . $input . "</div>";

// 正确
echo "<div>" . htmlspecialchars($input, ENT_QUOTES, 'UTF-8') . "</div>";
```

**SQL 注入的正确写法：**

```php
// 错误
$sql = "SELECT * FROM users WHERE id='$id'";

// 正确
$stmt = $mysqli->prepare("SELECT * FROM users WHERE id=?");
$stmt->bind_param('s', $id);
$stmt->execute();
```

**注意两者的共同点：**

> **都不是“过滤掉坏字符”，而是“让输入失去成为代码的资格”。**

- XSS：`htmlspecialchars` 把 `<` 变成 `&lt;`，浏览器不再当标签
- SQL：`prepare` 把参数当纯数据，数据库不再当语法

**过滤黑名单永远可以绕过，编码/参数化才是根治。**

## 六、学习顺序建议

| 阶段 | 学什么 | 为什么 |
| --- | --- | --- |
| 1 | **XSS** | 门槛低，能直观看到"代码被执行" |
| 2 | **SQL 注入** | 需要 SQL 基础，但套路固定 |
| 3 | **命令注入 / 文件包含** | 同一个病根，换了个位置 |
| 4 | **反序列化 / 模板注入** | 更隐蔽的"代码执行" |

**核心是理解一句话：**

> **凡是“用户输入被当作代码解析”的地方，就有注入。**

---

## 七、总结

### 一张表看完

| | XSS | SQL 注入 |
| --- | --- | --- |
| 病根 | 字符串拼接 | 字符串拼接 |
| 越界后变成 | HTML/JS 代码 | SQL 语句 |
| 执行者 | 浏览器 | 数据库 |
| 受害者 | 用户 | 网站 |
| 判断方法 | 看输入是否被原样输出 | 看报错 / 回显 / 时间 |
| 根本修复 | 输出编码 | 预编译 |
| 兜底 | CSP、HttpOnly | 最小权限、关报错 |

### 一句话

> **XSS 是"让浏览器执行我的话"，SQL 注入是"让数据库执行我的话"。**
>
> **同一句话，说给不同的对象听。**

### 学习上的建议

**记住“三个位置”，所有注入都能归类：**

```
用户输入
   ↓
┌─────────────┬─────────────┬─────────────┐
│   浏览器     │   数据库     │   系统命令   │
│    XSS      │  SQL 注入    │  命令注入    │
└─────────────┴─────────────┴─────────────┘
```

**学到新漏洞时，先问一句：这个输入最后被谁解析了？**
